# 引き渡し手順書（フェーズ 2 / 利用者が実施する検証）

**この文書は上から順に実行するためのものである。** 参照で飛ばさずに済むよう、
コマンドと判定基準はこの 1 本に書いてある。

**なぜこれが要るのか。** フェーズ 2 の実装・レビュー・修正は終わっている（`swift test` 921 件・失敗 0）。
**ここから先に残っているのは、エージェントには実施できない検証だけである**——
実機の権限、肉声、実際のアプリへの挿入が要る。

**この工程は形式ではない。** フェーズ 1 で同じことを実施したとき、実際に欠陥が 4 件出た
（要件定義書 §2.8.3 / §2.8.4 / §2.8.5）。

| 出たもの | 何だったか |
|---|---|
| 右 Option が存在しない配列 | 既定の PTT キーが物理的に押せなかった（L-8） |
| 121 字の発話の末尾 約 38 字が失われた | 確定待ちの定義が誤っていた（V-12。フェーズ 2 で塞いだ） |
| クリップボードが化けた | 復元待ち 120 ms が不足し、前の内容が貼られた（既定を 300 ms へ） |
| モデルが天気を捏造した | 整形の検査が「入力の変換になっているか」を見ていなかった |

**合成音声と代役の入力欄では、この 4 件は 1 件も出なかった。**

## 0. 危険な操作（着手前に必ず読む）

**次の操作は環境を壊す。この文書の手順には 1 つも含まれていない。**

| やってはいけないこと | 何が起きるか |
|---|---|
| **`EnableSecureEventInput()` を呼ぶ** | **OS 全体のキー入力が壊れる。** 呼びっぱなしにすると、そのプロセスを落とすまで他アプリの入力補助（テキスト展開・IME 補助）が効かなくなる。**この文書のどの手順にも含まれない** |
| `tccutil reset` を実行する | **付与済みの権限がすべて消える。** 付け直しが最初からになる |
| `CFBundleIdentifier`（`com.haruki1090.GhostVoice`）を変える | **TCC の許可が全部やり直しになる**。DR に焼き込まれているため（詳細設計書 §9）。システム設定の一覧には古い項目が残る |
| 権限を許可した後に `.app` を別のディレクトリへ移す | 許可が無効になりうる（**未実測** = V-18）。だから **先に置き場所を決めてから許可する** |
| フェーズ 1 でターミナルアプリへ与えた許可を外す | **CLI の `ghost-voice` が動かなくなる。** 移行が終わるまで外さない |
| ターミナルから `Ghost Voice.app/Contents/MacOS/GhostVoice` を直接叩く | ターミナルの許可を借りて動いてしまい、「動いているのに Finder から起動すると動かない」という切り分け不能な状態になる（アプリはこれを検出して警告する） |
| 段 5 の `probe.swift` を、保存していない文書・チャットの入力中の文・パスワード欄で走らせる | **その入力欄の内容を実際に書き換える。** 使い捨ての入力欄でのみ実行すること |

> **権限を付けた後、最初に 1 度だけ確かめること。**
> **`swift test` がフォーカス中のアプリへ文字を書き込まないこと。**
> 権限が無い機体では起こりえなかったが、付与後は起こりうる。
> M5a の計測（`GHOST_VOICE_MEASURE=1`）は挿入経路を差し替えて塞いであるが、
> **既定の `swift test` に実挿入が混ざっていないことが前提である。**
> 空のテキストエディタを最前面にした状態で `swift test` を 1 回走らせ、
> **何も書き込まれないこと**を目で確かめる。

> **既定の `swift test` は、一瞬（実測 17 ms）だけ OS 全体の secure input を有効にする。**
> `SystemPasteShortcutSender` が本当に `IsSecureEventInputEnabled()` を見ているかを
> 実際に有効化して確かめる検査が 3 件あるためで、`defer` で必ず戻す。
> **これは正規の検査であり、上の禁止事項とは別である。** ただし走っている間、
> 他アプリの入力補助が一瞬効かなくなりうる。

## 1. 最初にやること: 権限の付け直し

### 1.1 なぜ付け直しなのか

**`.app` はターミナルアプリの許可を 1 つも引き継がない。** 推測ではなく実測である
（2026-08-14。詳細設計書 §9）。同一の `.app` を 2 通りの経路で起動して照会しただけの結果:

| 照会項目 | ターミナルから実行ファイルを直接叩いた | `open` で `.app` を起動した |
|---|---|---|
| `AVCaptureDevice.authorizationStatus(for: .audio)` | `.authorized` | **`.notDetermined`** |
| `AXIsProcessTrusted()` | true | **false** |
| `CGPreflightListenEventAccess()` | true | **false** |
| `CGPreflightPostEventAccess()` | true | **false** |
| `getppid()` | ターミナルの pid | **1（launchd）** |

`.app` は Finder / Dock / `open` から起動された瞬間に**自分自身が責任プロセスになる**。
**フェーズ 1 で Terminal.app へ与えた 4 つは、`Ghost Voice` へ付け直すことになる。これは避けられない。**

### 1.2 付け直す 4 つ

| # | 権限 | システム設定のペイン | 何のためか | 無いとどうなるか |
|---|---|---|---|---|
| 1 | マイク | プライバシーとセキュリティ > **マイク** | 音を拾う | 押しても録音が始まらない |
| 2 | 入力監視 | プライバシーとセキュリティ > **入力監視** | 右 Option の押下を受け取る（`CGEvent.tapCreate` / `kTCCServiceListenEvent`） | **PTT がまったく反応しない** |
| 3 | アクセシビリティ（AX API） | プライバシーとセキュリティ > **アクセシビリティ** | フォーカス中の入力欄へ直接入れる（`kTCCServiceAccessibility`） | AX 直接挿入ができない |
| 4 | キー送出 | プライバシーとセキュリティ > **アクセシビリティ**（3 と同じトグル） | ⌘V を送る（`kTCCServicePostEvent`） | ⌘V を送れず、テキストはクリップボードに残るだけになる |

> **アクセシビリティのトグル 1 つの裏に TCC のレコードは 2 つある**
> （`kTCCServiceAccessibility` と `kTCCServicePostEvent`）。
> **片方だけ有効な状態は原理的にありうる**ので、アプリは 2 つを別々に照会して案内する。
> ログの権限一覧が 4 行あるのはそのためである。

音声認識（`SFSpeechRecognizer`）の許可は**要らない**——`SpeechAnalyzer` はこの TCC を要求しない
（実測 V-14）。`--check` に音声認識の行が無いのは実装漏れではない。

### 1.3 手順（上から順に。所要 10 分）

#### 手順 1: 組み立てる

```bash
cd /path/to/ghost-voice
Scripts/make-app.sh
```

最後に `codesign -d -r-` の出力（designated requirement）が表示される。**ここを見る。**

- **`identifier "com.haruki1090.GhostVoice" and anchor apple generic and …` になっていること。**
- **`cdhash` という語が出ていたら止まる。** ad-hoc 署名になっている。
  `security find-identity -v -p codesigning` で Apple Development 証明書があるかを確かめる。

#### 手順 2: 置き場所を決める（**後から変えない**）

```bash
cp -R ".build/app/Ghost Voice.app" /Applications/
```

**TCC のレコードはアプリのパスも見る。** `~/Downloads` で許可してから `/Applications` へ移すと
許可を付け直す羽目になりうる（**移動で無効になるかは未実測** = V-18）。
**許可より先に置き場所を決めること。**

#### 手順 3: 起動して、要求を出させる

```bash
open "/Applications/Ghost Voice.app"
```

- **マイクのダイアログが出たら「許可」を選ぶ。** 4 つのうちここだけがダイアログで完結する。
- 入力監視とアクセシビリティは、アプリが要求を出した時点で**システム設定の一覧に載る**。
  **その場では許可されない。載せることが目的である。**

#### 手順 4: システム設定で 2 つのトグルを入れる

1. **システム設定 > プライバシーとセキュリティ > 入力監視** → `Ghost Voice` を**オン**
2. **システム設定 > プライバシーとセキュリティ > アクセシビリティ** → `Ghost Voice` を**オン**
   （このトグル 1 つが 3 番と 4 番の両方を担う）

**一覧に `Ghost Voice` が出てこない場合**は、手順 3 に戻って一度起動し、要求を出させる。
それでも出なければ署名を疑う（`codesign --verify --strict "/Applications/Ghost Voice.app"`）。

#### 手順 5: 終了して起動し直す（**必須**）

アクセシビリティ系の許可は**プロセスの起動時に読まれる**ので、付与しただけでは反映されない。

```bash
osascript -e 'quit app "Ghost Voice"' 2>/dev/null || pkill -f "Ghost Voice.app/Contents/MacOS/GhostVoice"
open "/Applications/Ghost Voice.app"
```

#### 手順 6: 確認する（**ここが判定**）

`LSUIElement` なので標準エラーはどこにも出ない。unified log で読む。

**`log` は必ず `/usr/bin/log` と絶対パスで書くこと**（この機体では同名のシェル関数と衝突する。
2026-08-15 実測）。この文書のすべての例がそうなっている。

```bash
/usr/bin/log show --last 2m --info --predicate 'subsystem == "com.haruki1090.GhostVoice"' --style compact
```

**権限一覧の 4 行すべてに ✓ が付いていること。** 3 行で先へ進まないこと——
**アクセシビリティとキー送出は別レコードなので、片方だけ ✓ という状態がありうる。**

#### 手順 7: フェーズ 1 の許可は外さない

ターミナルアプリへ与えた 4 つは、**この文書の検証がすべて終わるまで外さないこと。**
段 1 で `.app` が動かなかったとき、「権限側の問題か実装の問題か」を切り分けるために
CLI（`ghost-voice`）が動く状態が要る。

### 1.4 うまくいかないときに疑う順序

| 症状 | 疑うところ |
|---|---|
| PTT がまったく反応しない | 入力監視。**起動し直したか**（許可は起動時に読まれる） |
| 文字が入らずクリップボードに残る | アクセシビリティ（＋キー送出）。secure input が有効な欄（パスワード欄）ではないか |
| 一覧に `Ghost Voice` が出てこない | 一度起動して要求を出させる。それでも出なければ `.app` の署名 |
| ビルドし直したら許可が外れた | designated requirement が変わっている。`codesign -d -r-` に `cdhash` が出ていないか（＝ ad-hoc 署名になっていないか） |
| バンドル ID を変えた | **全部やり直しになる。変えないこと** |
| HUD が 1 度も出ない | **まず `pkill -9 -x GhostVoice` で落としてから** `--hud-check` を実行し、`pgrep` で PID が変わったことを確かめる（走っている `.app` には `open … --args` が届かない。実測）。次にログの 3 行を見る: `[HUD] 表示先:`（無ければ窓を作れていない）/ `[HUD] 状態の購読を開始しました`（無ければ録音しても何も届かない）/ `[HUD] 窓を出しました: …`（無ければ order-in されていない＝描画ではなく配線の側） |
| HUD が外部ディスプレイに出る | **内蔵が見つかっていない**（クラムシェル）。ログの `[HUD]` が「内蔵ディスプレイが見つかりません」と言っているはず |
| HUD がメニューバーの項目を隠す | 帯の左右は透明のはずなので、隠しているなら不具合。ログの `中心 x=` と切り欠きの位置がずれていないか |

## 段 1: V-19 — `CGEventTap` が実際にイベントを届けるか

> **これが不成立なら、PTT がまったく動かない。器（`NSApp.run()` の下で常駐する形）の
> 作り直しになる。段 3 以降の検証は 1 つも意味を持たない。**

### 【実機でしか判らない】

**何を確かめるのか。** `NSApplication.run()` の下で `CGEvent.tapCreate` が作ったタップに、
実際のキーイベントが配送されるか。

**どこまで判っていて、どこからが未実測か。**

- **判っている（実測 2026-08-14 / M3 / macOS 26.5.2）**: 疑いの本体だった
  「`NSApplication.run()` が `CFRunLoopGetMain()` を `.commonModes` で回すか」は**成立する。**
  タップを作らずに、`CFMachPort` 由来の version 1 ソース（**タップと完全に同じ形**）で確かめた。
  メニュー追跡中・モーダル中・`LSUIElement` の `.app` バンドル内でも発火し、
  陰性対照（`.defaultMode` にだけ足したソース）は同条件で 0 回だった。配送遅延 p50 0.045 ms
  （**正本は §13 の V-19**）。
- **未実測**: **タップ固有の振る舞い。** `CGEvent.tapCreate` は入力監視の権限ダイアログを
  誘発するので、開発中は 1 度も呼んでいない。次の 3 つはまだ誰も見ていない:
  1. タップが実際にキーイベントを配送するか
  2. `return nil` による抑止（録音中の ESC）が効くか
  3. `.tapDisabledByTimeout` が出ないか

### 手順

```bash
open "/Applications/Ghost Voice.app"
```

1. テキストエディタ（**使い捨ての窓**）を最前面にする。
2. **右 Option を押しながら短く喋って、離す。**
3. 文字が挿入されれば **成立**。

**まったく反応しなければ不成立**——ただし、その前に**権限側の問題と切り分ける**こと:

```bash
# フェーズ 1 の CLI が動くか（ターミナルアプリの許可を使う）
swift build && .build/debug/ghost-voice --check    # 4 項目すべてに ✓ が付いていること
.build/debug/ghost-voice --mic-check               # 「マイクは開けています」と出ること
.build/debug/ghost-voice                            # ここで PTT が動くなら実装は生きている
```

> **`--check` の終了コード 0 は最低条件にすぎない。** 終了コードが見ているのは
> 「PTT が動くか」（マイクと入力監視）だけで、**アクセシビリティが無くても 0 になる。**
> **4 行すべてに ✓ が付いていることを目で確かめること。**

> **`--request-permissions` を使う場合、マイクの行で最大 60 秒沈黙したら、
> そのターミナルアプリにはマイクの許可が無い。** 素の実行ファイルからは TCC のダイアログを出せず、
> `requestAccess` のコールバックが返らないためである（詳細設計書 §3.3）。
> **許可済みの別のターミナルから起動すること。**

- **CLI では動くが `.app` では動かない** → **V-19 が不成立。** `NSApplication.run()` との
  組み合わせが原因である。対処の候補は `CGEventTapHotkeyMonitor` の `runLoop:` を差し替えて
  専用スレッドで回す形（`RunLoopEntry` の構造は残せる）。
- **CLI でも動かない** → 権限側。段 1.4 の表へ戻る。

`.tapDisabledByTimeout` は unified log に出る。長め（10 分ほど）に常駐させてから見る:

```bash
/usr/bin/log show --last 15m --info --predicate 'subsystem == "com.haruki1090.GhostVoice"' --style compact | grep -i "tap"
```

**結果の記入先**: 詳細設計書 §13 の **V-19** の行。

> **番号について。** 引き渡しの指示では「V-16（`CGEventTap` が届くか）」と呼ばれていたが、
> **§13 の正本では V-19 がこの項目で、V-16 は「再ビルドで許可が残るか」である。**
> この文書は §13 の番号に従う。

## 段 2: V-16 / V-34 — 許可が再ビルドを跨ぐか、終了で発話を失わないか

### V-16: 再ビルド・再署名の後も許可が残るか

#### 【実機でしか判らない】

**何を確かめるのか。** コードを変えて再ビルド・再署名した `.app` が、付与済みの 4 つの許可を
そのまま保つか。

**なぜここに置くか。** 不成立なら、**段 3 以降でコードを 1 行直すたびに権限を付け直すことになる。**
何時間も測ってから気付くより、ここで判るほうがよい。

### V-34: 発話の途中の終了要求で発話が失われないか

#### 【実施済み（2026-08-15 / M3 / macOS 26.5.2）。ただし実発話の 1 回は残っている】

**何を確かめるのか。** 終了要求（⌘Q / SIGTERM / `osascript` の quit / ログアウト）が
来たとき、**進行中の発話を最後まで見届けてから終了するか。**

**なぜ重要か。** 挿入の途中でプロセスが落ちると、**⌘V の送出後・クリップボードの復元前**で
テキストがどこにも残らない。**発話が消える経路である。**

**防御の形**: `applicationShouldTerminate` が `.terminateLater` を返し、
`GhostVoiceCore.Shutdown.perform` が待機へ戻るまで待ってからホットキーを止める
（**CLI と同じ 1 つの実装**）。

> #### この項目の前提が一度崩れた（`bug-term`。2026-08-15）
>
> **「`--shell-only` では発話が無いのでこの経路を通らない——実発話でしか確認できない」**
> と書いてあったため、**この項目は実バンドルで一度も測られないまま出荷された。**
> その結果、利用者の実機で **`Ghost Voice.app` が `SIGTERM` でも `pkill` でも
> 終了しなくなった**（`kill -9` しか効かない）。発話は 1 つも抱えていなかった。
>
> 原因はシグナルの受け口が `DispatchSource(queue: .main)` だったこと。
> ハンドラが**メインキューのブロックとして**走り、その中で `.terminateLater` の
> 入れ子のランループへ入るので、**返事を出す `Task`（＝メインキュー）が永久に走らない。**
> libdispatch はメインキュー排出中の再入を拒む（`MainRunLoopHop` の注記に実測表がある）。
>
> **この文書の書き方そのものが欠陥の温床だった。** そこで
> **マイクにもキー監視にも触らずにこの経路を通す入口 `--shutdown-check` を足した。**
> 以下の手順はそれを使う。

#### 手順 A: 終了要求が効くか（**TCC に触れない。何度でも回せる**）

```bash
Scripts/make-app.sh --debug --output /tmp/gv-check
# 抱えていないときの終了
open -n "/tmp/gv-check/Ghost Voice.app" --args --shutdown-check=0
# 発話を 3 秒抱えたまま終了要求を受ける
open -n "/tmp/gv-check/Ghost Voice.app" --args --shutdown-check=3
```

起動したら、別のターミナルから終了要求を送って**所要時間を測る**:

```bash
PID=$(pgrep -f "gv-check/Ghost Voice.app/Contents/MacOS/GhostVoice" | head -1)
time kill -TERM $PID                        # SIGTERM
osascript -e 'tell application id "com.haruki1090.GhostVoice" to quit'   # ⌘Q・ログアウト相当
/usr/bin/log show --last 2m --info --debug \
  --predicate "subsystem == \"com.haruki1090.GhostVoice\" AND processIdentifier == $PID" \
  --style compact
```

**判定**:

- `--shutdown-check=0`: **1 秒以内に終わること**
- `--shutdown-check=3`: **約 3 秒待ってから終わること**（＝抱えていた発話を見届けた）
- ログに `[終了] 進行中の発話を待っています…` → `[素振り] run() が戻りました` →
  `[終了] Ghost Voice を終了しました。` が**この順で並ぶこと**
- **`--shutdown-check=3` では、待っている間 1 秒ごとに
  `[終了] まだ待っています。**PTT キーを離してください。**（残り N 秒）` が出て、
  N が 1 秒ずつ減っていくこと。** 残りが動いていること自体が
  「メインが詰まっていない」の証拠である（2026-08-15 の欠陥はまさにそこが死んでいた）
- **文言に `10.0 seconds` のような英語が 1 つも混ざらないこと**（すべて「10 秒」の形）

**実測（2026-08-15 / M3 / macOS 26.5.2 / debug ビルドの実バンドル）**:

| 終了要求 | 修正前 | 修正後 `=0` | 修正後 `=3` |
|---|---|---|---|
| `SIGTERM`（`kill -TERM` / `pkill`） | **終わらない**（30 秒待って `kill -9`） | 0.13 秒 | 3.15 秒 |
| `SIGINT`（Ctrl-C 相当） | **終わらない** | 0.18 秒 | 3.16 秒 |
| `osascript` の quit（＝ログアウト・⌘Q と同じ Apple Event 経路） | 0.24 秒（**効いていた**） | 0.23 秒 | 3.34 秒 |
| ⌘Q（メニューバー項目「Ghost Voice を終了」） | **未実測** | **未実測** | **未実測** |

> **⌘Q が未実測な理由。** `LSUIElement` なのでアプリは活性化せず、⌘Q が届くのは
> **メニューバーのメニューを開いている間だけ**である。打鍵の送出には `CGEvent.post` が要り、
> 利用者の実機では禁止されている。**経路としては `osascript` と同じ**
> （どちらもメニュー動作・Apple Event というランループのイベント配送から
> `NSApp.terminate(nil)` を呼ぶ）ため、この欠陥の影響は受けない——
> 実際、修正前でも `osascript` は効いていた。

#### 手順 B: 実発話での 1 回（**これは今も実発話でしか測れない**）

手順 A は「終了の段取りが通ること」を測る。**本物の確定・整形・挿入が
猶予の中で完走することは、実発話でしか測れない。**

```bash
open "/Applications/Ghost Voice.app"
```

1. **右 Option を押している最中に**、別のターミナルから:
   ```bash
   pkill -TERM -f "Ghost Voice.app/Contents/MacOS/GhostVoice"
   ```
2. **キーを離すまで終わらないこと。**
3. **HUD に `終了待ち: PTT キーを離してください（残り N 秒）` が出ること**（下記）。
4. 離すと確定 → 整形 → 挿入まで走ってから終了すること。**テキストが消えないことが要点。**
5. **わざと離さずに 10 秒使い切る回も 1 度やること**（下記）。

**実測（2026-08-15 / M3 / macOS 26.5.2 / 利用者の実機）: 手順 B を 1 回通し、欠陥が 2 件出た。**

| 見えたこと | 何が起きていたか | 直し方 |

| **「一応キルをしているんですけれども全然反応しません」**（キーを押したまま） | 段取りは正しく待ち、正しい文言を出していた。**しかし `.app` では unified log にしか出ず、画面には何も出なかった。** 利用者は「キーを離してください」を一度も見ないまま猶予 10 秒を使い切った | **HUD に出す。** 1 秒ごとに残り時間を更新する（詳細設計書 §7.4「終了待ちを HUD に出す」） |

#### 手順 C: 猶予を使い切ったときにテキストが残るか（**実発話。手順 B の続き**）

**これが「発話を失わない」の最後の砦である。**

1. `open "/Applications/Ghost Voice.app"`
2. **右 Option を押して喋り続ける。** 押したまま、別のターミナルから
   `pkill -TERM -f "Ghost Voice.app/Contents/MacOS/GhostVoice"`

     が出ること

## 段 3: V-4 / V-42 — キーの副作用と、打鍵の捕獲

### V-4: 右 Option 押しっぱなしの副作用

#### 【実機でしか判らない】

**何を確かめるのか。** PTT キーを押しっぱなしにする間、下流アプリが壊れないか（R-1）。
**ESC の抑止が、抑止すべき窓でだけ効いているか。**

**なぜ重要か。** #1 が実用上つらければ **PTT の方式そのものを変える**（2 回連続押下でトグル）。
#5〜#7 は「ESC を奪ってアプリの操作を壊していないか」で、**奪いすぎても、奪えなさすぎても欠陥である。**

> **caps lock を Option へ転用している場合、#1 と #3 の意味が変わる。**
> #1（PTT キーを押しながら `a`）は caps lock では起こらない副作用なので、
> **本物の右 Option がある機体でのみ判定できる**——転用機では「該当なし」と記録する。
> #3 は**転用機でこそ意味がある**（転用した caps lock が本物の左 Option と左右を取り違えないことの確認）。

#### 手順

`Ghost Voice.app` を通常起動し、**使い捨ての**テキストエディタを開いて順に試す。

| # | 操作 | 期待 | 実測 |
|---|---|---|---|
| 1 | 右 Option を押しながら `a` を打つ | `å` が入る（既知の副作用 R-1。**実用上つらいかを判断する**） | |
| 2 | 右 Option を押して離す（発話なし） | 「認識できませんでした」が出て、何も挿入されない | |
| 3 | **左 Option を押したまま**右 Option を押して離す | **録音が止まること**（左右のデバイスビットを実キーボードが立てているかの確認。詳細設計書 §2.3） | |
| 4 | ⌘C / ⌘V を通常どおり使う | 影響なし | |
| 5 | **録音中**に ESC を押す | 中断され、**ESC が下流アプリへ届かない**（エディタの入力が中断されない） | |
| 6 | **録音していないとき**に ESC を押す | 下流アプリへ**届く**（ESC を奪っていないこと） | |
| 7 | **キーを離した直後**（確定中 / 整形中）に ESC を押す | **中断され**（挿入されない・履歴は `notInserted`）、**かつ ESC が下流アプリへも届く** | |

**外れたときにどうするか**

- **#1 が実用上つらい** → `HotkeyDecision.decide` を「右 Option の 2 回連続押下でトグル開始 /
  再押下で停止」へ差し替える。**判定は純粋関数なので、`HotkeyDecision` とそのテストだけを直せばよい。**
- **#3 で録音が止まらない** → その入力源はデバイスビットを報告していない。
  `ModifierSide` の退避経路に落ちているので、**詳細設計書 §2.3 の記述を実測に合わせて直す。**
- **#7 が効かない** → 監視器が処理中の窓を知らない（`setSessionBusy` が届いていない）。
- **#7 で ESC が下流へ届かない** → 逆に、その窓で抑止してしまっている。
  どちらも `HotkeyDecision.decide` と `DictationSession` の `setSessionBusy` の呼び出しを見る。

**結果の記入先**: 詳細設計書 §13 の **V-4**。

### V-42: 設定画面で打鍵を捕まえられるか

#### 【防御済み・確認のみ】

**何を確かめるのか。** 設定画面の「変更…」で PTT / Undo キーを打鍵から設定できるか。

**防御の形**: **2 本目のタップを立てず、既存の監視器を「捕獲モード」へ入れている。**
捕獲モードのイベントは `HotkeyDecision.decide` を 1 度も通らないので、
**捕獲中に PTT / Undo / ESC の中断が発火しえない**（構造で保証。合成イベントで本物の
`handle` を通す検査で固定してある）。**残るのは実キーボードでの捕獲そのものだけである。**

#### 手順

メニューバーのマイクのアイコン（`Ghost Voice`）→ **設定…** → ホットキーの「変更…」。

3. 捕獲中に**他アプリへ打鍵が漏れていない**か（画面に「いま打鍵を待っています」と出る間、
   背後のエディタに文字が入らないこと）
4. **ESC で取りやめられる**こと
5. 保存すると**その場で監視器へ反映される**こと（再起動が要らない）

### V-3: 主要アプリでの挿入経路

#### 【実機でしか判らない】

**経路の読み方**

- `clipboardOnly` … どちらも使えず、クリップボードに残しただけ。**復元待ちを延ばしても直らない。**
  権限（キー送出とアクセシビリティ）を確認する。
- `notInserted` … 中断（ESC）された発話。**および終了の猶予切れで打ち切った発話**——そちらは `isProvisional` が真で、履歴画面に「暫定（確定前）」のバッジが付く（V-34 の手順 C）。

#### あわせて確認する 4 つ

1. **クリップボードが元に戻るか。** リッチテキスト（ブラウザからコピーした文字）や画像を
   クリップボードへ入れた状態で挿入し、**挿入後に元の内容が戻っている**こと。
   **`NSPasteboard: synchronous promise fulfillment requested from a background thread!` の
   警告で遅延や失敗が出ないか**も見る（他アプリのファイル約束など、提供元が別プロセスの場合）。
2. **`CGPreflightPostEventAccess()` と実際の送出可否が一致するか。** `canSend` が true を返しつつ
   ⌘V が届かない場合、**「発話が消えたうえに成功として記録される」経路が再発する。最初に確かめること。**
3. **`[metrics]` の `insert` と `total`。** Pasteboard 経路では復元待ち（既定 300 ms）が乗るので、
   AX 経路（0.1〜5.5 ms）とは桁が変わる。**これは劣化ではなく、測っている量が変わっただけである。**
   `total` が 1000 ms（NFR-P6a）に収まるかを見る。
4. **V-15（アイドル時の CPU / NFR-P7）を同じ機会に取る。** `AVAudioEngine` を起動したまま
   常駐する設計なので、**測るまで判らない。**

   ```bash
   top -pid $(pgrep -f "Ghost Voice.app/Contents/MacOS/GhostVoice") -stats pid,cpu,mem
   ```
   **1 分見て 1 % 未満であること。** 【実機でしか判らない】。記入先は §13 の **V-15**。

### 復元待ち 300 ms の上限（V-3 の付帯。**この段で必ず見る**）

#### 【実機でしか判らない】

**判っていること**（**正本は詳細設計書 §6.3 の「復元待ち時間の根拠」**）: **120 ms では壊れ、300 ms では壊れない。それだけである。**
間の値も、より重いアプリも測っていない。実測の 35 ms は自プロセスの軽い `NSTextView` に対する
値で、**WindowServer を経由する分の遅延を含まない下限にすぎない。**
**300 ms で足りることを確かめたのは cmux 1 本だけである。**

**なぜこの値が重いのか——3 つのものの幅を同時に決めている。**

1. **貼付が成功するかどうか。** 短すぎると相手が ⌘V を処理する前に復元が走り、
   **前のクリップボードの内容が貼られる**（履歴には正しい発話が成功として残る）。
2. **Undo が使えない窓の幅。** Pasteboard 経路は「退避 → ⌘V → **復元待ち** → 復元」の間
   クリップボードを握っており、**その待ちのあいだ `DictationSession` の actor は解放されている。**
   その窓で Undo キーが届くと、縮退が置いた生テキストを復元が上書きしてしまうので、
   **その間の Undo は `.undoUnavailable` へ倒している**（基本設計書 §18 / 詳細設計書 §6.5）。
   **つまり復元待ちを伸ばすと、Undo が使えない時間もそのぶん伸びる。**
3. **プロセスを落としてはいけない窓の幅。** ⌘V の送出後・復元前に落とすと、
   テキストがどこにも残らない（ESC が挿入開始後に効かないのはこのためである）。

**確かめること**

- 段 4 で回った全アプリで**貼付が空振りしていない**こと。
  **1 つでも空振りするなら値をさらに上げる**（速さより余裕を優先する。壊れ方がデータの取り違えであるため）。
- **値を下げようとしないこと。** 120 ms は「据え置いてよい値」ではなく
  **実機で事故を起こして棄却された値である。**

**記入先**: 詳細設計書 §11.3 の 1 番と、§6.3 の「採った値」。

| **V-35** | 押下だけを抑止し、**対になる解放は下流アプリへ届く**（マスクに `keyUp` を足すと全打鍵の配送量が倍になるため）。**文字キーの単独の解放を意味づけるアプリで異常が出ないか** | ⌃⌘Z を使うアプリで、Undo 以外の挙動が壊れないか | 同上 | 壊れるアプリがあれば §2.1 の判断を事実に合わせて直す |
| **V-36** | 長い発話をして、**書き換わる直前に PTT を押す** | 次の録音の開始が遅れて感じられるか。**差し替えは actor の外で走る**ので、AX が遅い相手でも待たされないはず | 【防御済み・確認のみ】 | 体感できるほど遅いなら、まず `refinementApplyMode` を `beforeInsert` にして消えるか見る。消えるならこの経路が原因 |
| **V-30** | Pasteboard 経路のアプリ（Slack / Notion など）で挿入した直後に、その範囲を読み戻せるか | 読み戻せれば **(a) の分岐を Pasteboard 経路へ広げられる** | 【実機でしか判らない】 | **読み戻せないなら FR-7（Undo）はこの経路で成立しない**（現状の裁定どおり。縮退のまま） |

### V-36 の背景（なぜ【防御済み】なのか）

**対処前は待たされる量がほぼ `12 × AX 1 往復`** で、AX の上限（1 往復 0.5 秒）に当たる相手では
**最大約 6 秒 actor が塞がり、その間の PTT が処理されず発話が丸ごと落ちていた。**
フェーズ 2 で差し替えを actor の外へ出した（`runOffActor`。重なりは世代の錠が塞ぐ）結果、
1 往復 10 ms を注入した相手で **最大 164 ms → 3.1 ms** になった（実測 2026-08-15。**正本は §10.1**）。
**残るのは実アプリでの 1 往復のコストだけで、これは V-28 の挿入所要として測れば足りる。**

### V-45: 整形が効いているかを自分で確かめる（**5 分。権限は要らない**）

**「整形が効いていない気がする」を数字にするための最短手順である。**
2026-08-15 の実運用では 10 発話中 2 件しか整形されず、しかも**その 2 件は
モデルが入力をそのまま返した回**だった（要件定義書 §2.8.9）。
**「`refinedText` がある」と「整形が意味のある変化を起こした」は別である。**

#### 手順 1: 履歴を読む（**読むだけ。書き換えない**）

`Ghost Voice.app` を通常起動し、**フィラー（「えー」「あの」「まぁ」）を混ぜて**
**10〜40 字くらいを 5 回**喋る。**1 回ごとに 30 秒以上あけること**——
間隔が空いた状態こそが実運用であり、詰めて喋ると問題が見えない。

```bash
python3 - <<'EOF'
import json, pathlib
p = pathlib.Path.home()/'Library/Application Support/GhostVoice/history.json'
d = json.loads(p.read_text())          # d[0] が最新（append は先頭挿入）
print(f"{'時刻':20} {'字数':>4} {'経路':11} 整形")
for e in d[:10]:
    raw, ref = e['rawText'], e.get('refinedText')
    if ref is None:      state = 'なし（打ち切り or 検査が落とした）'
    elif ref == raw:     state = 'あり（ただし1字も変わっていない）'
    else:                state = f'あり → {ref!r}'
    print(f"{e['timestamp']:20} {len(raw):>4} {e['insertionMethod']:11} {state}")
EOF
```

**読み方**

| 出た結果 | 意味 | 次にすること |
|---|---|---|
| **「あり → …」が 5 回中 4 回以上** | **正常。** 整形は効いている | 終わり |
| **「なし」が多い** | 打ち切りか、検査が落としたか。**手順 2 で切り分ける** | 手順 2 |
| **「あり（ただし1字も変わっていない）」ばかり** | モデルが仕事をしていない。フィラーを混ぜて言い直す（入力に直す所が無ければ、返ってくるのは同じ文である） | 発話を変えて再実行 |
| **`経路` が全部 `pasteboard`** | **(b) の分岐**（打ち切り 750 ms）で走っている。**これが既定の使い方である**（要件定義書 §2.8.9） | 参考情報として記録 |

#### 手順 2: 打ち切りか、検査かを切り分ける（`.app` を起動せずに行える）

**上で「なし」になった発話の生テキストを、そのまま整形器へ通す。**
マイクも権限も使わない。**利用者の履歴は読むだけである。**

```bash
cd <ghost-voice のワークツリー>
swift test --filter "実機の Apple Intelligence による整形" 2>&1 | tail -40
```

これは**既定で走る実機検査**で、次の性質を持つ。

- **モデルが応答しない**（打ち切り・`guardrailViolation`）→ **失敗にしない**。縮退として扱う
- **応答はあったのに検査が捨てた** → **失敗**。これが「検査が厳しすぎる」の印である

**全部緑なら、落ちているのは検査ではない。打ち切りである。**

#### 手順 3: 打ち切りだった場合に見るもの

**発話と発話の間隔を変えて、同じ長さの発話を 3 回ずつ試す。**

| 試すこと | 期待 | 外れたら |
|---|---|---|
| **前の発話の直後（5 秒以内）**に 20 字を喋る | `refinedText` が入る | 報告する（暖機以前の問題） |
| **1 分以上あけて**同じ 20 字を喋る | **これも `refinedText` が入る**（押下で暖め直しているため） | **報告する。** 押下時の暖機（詳細設計書 §5.2）が効いていない |
| **80 字以上**を 1 分あけて喋る | 入らないことがある（温まっていても 365 + 5.26×字 で 750 ms を割る） | **設計どおり。生テキストは欄に残る** |

> **効かなくても発話は失われない。** 整形が間に合わなければ**生テキストがそのまま挿入され**、
> 履歴には `rawText` が必ず残る。**整形が信用できないと感じたら、設定で
> `整形を有効にする` を切ってよい**——挿入は速くなり、内容は認識結果そのままになる。

**結果の記入先**: 詳細設計書 §13 の V-45（新設）。

### あわせて見る: 整形が捨てられていないか

**整形の許容量は「入力に無い文字を 1 字も足さない」まで絞ってある。**
次の 2 つは、その絞りが厳しすぎないかを見る。

| やること | 見るもの | 外れたときにどうする |
|---|---|---|
| **40 字以上の発話**を、**言い終えてから離す**のと**言い終える前に離す**のとで各 5 回 | 履歴の `refinedText` が入っているのに欄が生テキストのままなら**差し替えの断念**、`refinedText` が空なら**整形そのものが捨てられている** | **言い終えた側で `refinedText` が空になるなら報告する**（整形の検査が厳しすぎる）。**言い終える前に離した側が空になるのは設計どおり**——モデルが続きを捏造するので捨てている。**生テキストは欄に残る** |
| **数字を含む発話**（「十時から」「百二十パーセント」「一万円」など）を各 3 回。**英語の発話も 3 回** | 履歴の `refinedText` が入っているか | **数字の発話で空になるなら報告する**——整形プロンプトの規則（数字の表記を変えない）が実機で効いていない。**英語で空になるのは既知**（6 発話中 2 が日本語へ訳され、検査が落とす）。**どちらも生テキストは欄に残る** |

> **原理的に捕まえられないものがある（直っていない。安全網で受ける。正本は要件定義書 §2.8.8）。**
> 整形の検査は「**足された文字**」しか見ない。**削ることで意味が変わる逸脱は原理的に通る**——
> 「行きたくないです」→「行きたいです」（否定の脱落）、
> 「…が抜けてるのでそこを追加したいです」→「…を追加したいです。」（削るだけの要約）。
> **指標の改良では解けない**（文字の編集距離は意味を見ていない）。
> 安全網は **FR-7（Undo）** と **履歴が `rawText` を必ず保持していること** の 2 つである。
> **整形が信用できないと感じたら `refinementEnabled` を `false` にできる。**

**結果の記入先**: 詳細設計書 §13 の **V-28 / V-29 / V-30 / V-35 / V-36**。
**整形が捨てられていないか**の 2 行は V-x 番号を持たないので、詳細設計書 §5.5.1 へ追記する
（V-37 は 2026-08-15 に閉じており、これはその後の残りである）。

## 段 8: V-1 — 肉声での認識精度

### 【実機でしか判らない】

**何を確かめるのか。** `DictationTranscriber`（既定）と `SpeechTranscriber` の、**肉声での**精度比較。

**なぜ重要か。** **これで `transcriberKind` の既定を変えるかが決まる。**
合成音声では `dictation` が優位だった（CER 3.02 % 対 3.21 %。**正本は §11.2**）が、**差は 0.19 ポイントしかない。**
肉声で逆転する可能性は否定できない（R-2）。

1. 同じ内容を 10 回以上、**両方の設定で**喋る。設定画面（または `settings.json`）で

3. **どちらが良かったかを書く。** 差が付かなければ「差が付かなかった」と書く。
