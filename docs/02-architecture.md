| # | 方針 | 理由 |

| 1 | コアロジックを Swift Package に分離し、アプリは UI と OS 統合のみを担う | NFR-M2（テスト容易性）、NFR-M3（OSS 公開） |

## 4. 状態遷移

**確定の後は 2 本に分かれる。** 分かれ目は「挿入先が差し替え可能と判定できたか」だけである
（要件定義書 §2.8.6 / FR-5 の細目）。

```
                    ┌──────────┐
          ┌────────▶│   idle   │◀───────────┬───────────┐
          │         └────┬─────┘            │           │
          │              │ キー押下          │           │
          │              ▼                  │           │
          │        ┌──────────┐             │           │
          │        │recording │             │ 完了 / 中断 │
          │        └────┬─────┘             │           │
          │             │ キー解放           │           │
          │             ▼                   │           │
          │       ┌───────────┐             │           │
          │       │finalizing │             │           │
          │       └─────┬─────┘             │           │
          │             │ 確定テキスト取得    │           │
          │             ▼                   │           │
          │      ┌─────────────┐            │           │
          │      │ 経路判定     │            │           │
          │      └──┬───────┬──┘            │           │
          │   差し替え可 │       │ 差し替え不可  │           │
          │         ▼       ▼               │           │
          │  ┌───────────┐ ┌───────────┐    │           │
    生テキスト  │ inserting │ │ refining  │    │           │
    で縮退     │ （生）     │ └─────┬─────┘    │           │
          │  └─────┬─────┘       │ 整形完了   │           │
          │        │             ▼           │           │
          │        │       ┌───────────┐     │           │
          │        │       │ inserting │─────┘           │
          │        │       └───────────┘                 │
          │        │                                     │
          │        └─▶ idle（ここで次の PTT を受け付ける）  │
          │              │                               │
          │              │ 整形が返る（保留タスク）          │
          │              ▼                               │
          │        ┌───────────┐                         │
          └────────┤ revising  │─────────────────────────┘
      差し替えを断念 └───────────┘  差し替え成功
```

| 状態 | HUD 表示 | 主な処理 |
|---|---|---|
| `idle` | 非表示（notch のまま） | 待機。AudioEngine は `start()` 済みで保持。**LLM セッションは保持しない**（温まっているのはデーモン側のモデル。§6） |
| `recording` | 展開＋音量インジケータ＋暫定テキスト | 音声取得と逐次認識 |
| `finalizing` | 「確定中」 | `finalizeAndFinishThroughEndOfInput()` |
| `refining` | 「整形中」 | LLM 整形。**差し替え不可の分岐でのみ通る。** 既定 750 ms を超えたら生テキストで縮退（§7） |
| `inserting` | 「挿入中」→ 完了表示 | AX 挿入、失敗時 Pasteboard フォールバック |
| **`revising`** | 「整形を反映中」 | **差し替え可能の分岐でのみ通る。** 挿入済みの生テキストを整形結果へ差し替える（詳細設計書 §8.3）。**断念しても生テキストは欄に残る** |

**`revising` は「忙しい」に数えない。** 保留中の差し替えがあっても次の PTT は受け付ける。
差し替えは書き込みの直前に照合し、次の発話の**挿入が始まった**時点で破棄する。
**破棄しても何も書き換えていない状態で終わる**（差し替えは「読む → 選ぶ → 書く」で、途中で捨てれば書き込みが起きない）。

**中断（ESC 押下）は、挿入が始まる前のどの状態からでも `idle` へ戻る。** 中断時、録音済み内容は破棄せず履歴に残す（発話を失わないため）。挿入していないので `insertionMethod` は **`.notInserted`** で記録する（`.clipboardOnly` で記録すると「クリップボードに残っている」という嘘になる）。整形は経ていないので `refinedText` は nil であり、Undo の対象にはならない。

> **ただし挿入を始めた後の ESC は受け付けない。** `inserter.insert(_:)` を呼んだ後に中断すると、⌘V を送出済みのままクリップボードの復元だけが走り、**テキストがどこにも残らない**（詳細設計書 §6.3 が潰した欠陥と同じ形）。**「中断が効かない」より「テキストが消える」ほうが重い**ので、ここは手遅れとして扱い完走させる。
>
> したがって中断が効くのは `recording` / `finalizing` / `refining` の 3 状態である。処理窓は実測 400〜800 ms あり、人が ESC を押すのに十分な長さがあるため、**録音中だけに限ってはならない**（限ると、ユーザーが「挿入するな」と押したのに挿入される）。
>
> **差し替えできる分岐（FR-5(a)）では、この窓が短くなる。** `refining` を通らずに挿入するので、
> 中断が効くのは `recording` / `finalizing` だけになる。**代わりに `revising`（保留中の差し替え）に対する
> ESC は「差し替えを取りやめる」として効く**——書き込みが 1 回も起きないので、これは安全な取消しである。
> **差し替えが始まった後の ESC は受け付けない**（範囲を選んだ直後に止めると選択だけが残る。§4.1 の 14）。

> **例外が 1 つある。処理中に PTT の押下が先着していると、その後の ESC は処理中の発話には届かない。** `run()` は `.pressed` を受けた時点で次の発話の準備に入り、そこで前の発話の完了を待つため、後続の `.cancelled` は処理が終わるまで配送されない。
>
> **ただし ESC が捨てられるわけではない。** 配送された時点では次の発話が録音中なので、**そちらが中断される**（実測で確認済み。`cancelAfterQueuedPressAppliesToNextUtterance` が固定している）。ユーザーは PTT を押し直して新しい発話を始めた後に ESC を押しており、「新しい方を止める」は読みとして妥当である。
>
> **塞がないことを選んだ。** 塞ぐには押下の経路も非同期にする必要があり、そうすると「押下は前の発話の完了を待ってから始める」という直列性——ESC を届かせるためにイベントループから外へ動かした、まさにその性質——を作り直すことになる。得られるのは「ESC の宛先が古い方に変わる」だけで、失う可能性のあるものは発話の取りこぼしである。**割に合わない。**

> **ここにも secure input の例外が及ぶ。** 「履歴に残す」は挿入経路を通らないので、§7 の例外を挿入側だけに実装すると**この経路からパスワードが `history.json` へ入る**。中断時も secure input が有効なら履歴へ残してはならない。

### 4.1 実装上の要点（`DictationSession`）

`Sources/GhostVoiceCore/Session/DictationSession.swift`。以下はいずれも実測に裏づけられている。

| # | 決めたこと | 理由 |
|---|---|---|
| 1 | **`begin()` を待ってからタップを張る** | `feed` は `begin()` 復帰前のバッファを黙って捨てる。逆順にすると**発話の頭が落ちる**（詳細設計書 §4.4）。`begin()` は実測 1.2〜1.4 ms なので待つ費用は小さい |
| 2 | **`stopTap()` → 供給タスクの完走 → `finish()` の順** | `removeTap` は端数バッファを配ってから返り、リサンプラは 231 フレーム（14.4 ms）を抱える。供給しきる前に `finish()` を撃つと解析器の入力はもう閉じており、**発話の末尾が落ちる**（詳細設計書 §3.4） |
| 3 | **整形は結果ストリームの終端で始める。`finish()` の復帰そのものは待たない** | **最初の `.final` で先へ進むと、その後に届いた確定が読まれず発話の末尾を失う**（V-12。実機の肉声で再現。要件定義書 §2.8.4）。待つのは「これ以上テキストが来ない」と判る時点である。終端は実測で `finish()` の復帰とほぼ同時（差 2 µs 未満）だが、復帰そのものを待つ設計にはしない——返らない認識器で録音が終わらなくなる（詳細設計書 §10 の M2） |
| 4 | **キー解放より前の `.final` では先へ進まない** | 長い発話では録音中にも確定が出る。これで進むと発話の後半を失う |
| 5 | **確定に締め切りを置く**（`finalizeDeadline`、既定 2 秒） | 認識器が黙り込んだり、**確定を出したままストリームを閉じ忘れたり**したときに録音が終わらなくなるのを防ぐ。締め切りに達したら、そこまでに積んだ確定（1 件も無ければ暫定テキスト）で先へ進む（空で捨てるよりは残す） |
| 6 | **最大録音時間**（`maxRecordingDuration`、既定 120 秒） | 混在入力源で解放を取りこぼす経路が残っている（詳細設計書 §2.3）。時間で抜ける道が要る。到達時は**中断ではなく確定**として扱う |
| 7 | **secure input は整形の手前でも見る** | 挿入時にしか見ないと、拒否する頃には発話が既に `FoundationModels` を通っている（§7 が挙げる害の 1 番目）。手前で弾けば整形にも履歴にもクリップボードにも渡らない |
| 8 | **確定〜挿入をキャンセルの効かないタスクで走らせる** | 下記 |
| 8b | **`run()` のイベントループは確定〜挿入を待たない** | 待つと処理中（実測 400〜800 ms）に届いた ESC がイベント列に溜まり、**中断が原理的に効かなくなる**。発話の直列性は次の押下側（`startRecording()` の頭）で待って保つ |
| 9 | **起動時、整形器の捨て推論は待たない** | `prewarm()` はコールド時に実測 1.9〜3.3 秒掛かる。待ってからホットキーを読み始めると**起動直後の数秒間、押しても何も起きない**（§6） |
| 10 | **認識器の `prepare` を発話ごとに呼び直さない** | ロケール変更は `prepareTranscriber(locale:kind:)` を明示的に呼ぶ形にし、**再試行の回数を人の操作の回数に縛る**（発話中に呼ぶと Core が `DictationSessionError.busy` を投げる）。**フェーズ 2 で枠の解放そのものも実装した**——`reserve` の後に失敗したら確保した枠を返し、成功したら前のロケールの枠を返す（持ち越し項目 5。詳細設計書 §4.3）。それまでは**相異なるロケールを 5 種類試すと回復不能**になっていた |
| 11 | **差し替え可能と判定した発話では、整形タスクを起動してから `await` せずに生テキストを挿入する** | FR-5(a)。整形をクリティカルパスから外すのが目的なので、待った時点で意味が消える |
| 12 | **保留中の差し替えは `isBusy` に数えない** | 数えると次の PTT が最大 3 秒待たされ、**差し替えのために発話を取りこぼす**ことになる。捨てても生テキストは欄にある |
| 13 | **差し替えは挿入の通し番号（epoch）で照合し、次の発話の挿入が始まった時点で破棄する** | 前の発話の差し替えが、次の発話のテキストの上に走るのを防ぐ。**破棄は常に「何も書き換えていない」で終わる** |
| 14 | **ESC は差し替えの「開始前」にしか効かせない**（保留中の取りやめは可、進行中の中止は不可） | 現行の「挿入より後で `isCancelRequested` を読まない」と同じ理由。範囲を選んだ直後に止めると選択だけが残る。**保留中の取りやめは書き込みが 1 回も起きないので安全である** |
| 15 | **secure input は差し替えの直前にもう一度見る** | 整形を待つ間にパスワード欄へ移りうる。**中止しても生テキストは既に欄にある**（挿入時点では secure input ではなかったので、新しい漏れではない） |
| 16 | **終了（`exit`）は保留中の差し替えを待たずに捨てる** | 待つと終了が最大 3 秒延びる。捨てても生テキストは欄にあり、整形結果は履歴にある |

> **8 について。** キャンセルされたタスクの中では `AsyncStream` の `next()` が即座に nil を返す（実測）。確定から挿入までをそういう文脈で走らせると、次が同時に起きる。
>
> - 供給の待ち合わせが即座に抜け、**発話の末尾が認識器へ届かない**
> - `withTimeout` が常に nil を返し、**整形が必ず縮退する**
> - `PasteboardInserter` の復元待ち（120 ms）が 0 になり、**⌘V が処理される前にクリップボードが戻って発話が消える**（詳細設計書 §6.3 が潰した欠陥の再発）
>
> これは机上の話ではなく、**最大録音時間の満了で確定へ入る経路が実際にこれを踏んでいた**（その経路の呼び出し元は、確定処理の入口で `cancel()` される当のタスク自身である）。アプリ終了時に処理中の発話を巻き添えにする経路も同じ形になる。非構造化タスク（`Task {}`）はキャンセルを継承せず、`Task<Void, Never>` の `value` は待つ側がキャンセルされても早く返らないので、そこへ逃がして直列性ごと守る。

## 6. ウォームアップ設計

実測により、初回コストが体感を大きく損なうことが判明している。

| 対象 | コールド | ウォーム | 対策 |
|---|---|---|---|
| `FoundationModels` | 1.906 秒（設計調査）／ 3.318 秒（Task 6） | **低負荷 0.389 秒 / 負荷下 0.461 秒**（中央値。最大 0.413 / 0.518 秒） | アプリ起動時に**捨て推論を 1 回通す**。`prewarm()` を呼ぶだけでは足りない。**セッションは常駐させず発話ごとに作る**（下記） |
| `AVAudioEngine` | **実測 327 ms（アイドル）／ 456 ms（CPU 負荷下）** | タップ着脱は**実測 0.07〜0.6 ms** | 起動時から `start()` 済みにし、録音開始時はタップの着脱のみ行う。**マイク未許可のまま `inputNode` に触れると実測 510 秒ブロックする**ため、`prepare()` は権限を先に確かめる（詳細設計書 §3.3） |
| `SpeechAnalyzer` | モデルロードあり | — | `prepareToAnalyze(in:)` を事前実行。`Options.modelRetention` に `.processLifetime` を指定しモデルを常駐させる |
| `CGPreflightPostEventAccess()`（キー送出の権限照会） | **実測 初回 16.7 ms** | 以降も **毎回 10.6 ms**（キャッシュされない） | 起動時に `PostEventAuthorization.shared.refresh()` を 1 回通し、以後は保持値を読む。**この API は他と違いウォームアップでは安くならない**ので、キャッシュ側で解決する（詳細設計書 §9） |
| `IsSecureEventInputEnabled()` | **実測 初回 23.8 ms** | **0.000 ms** | 起動時に 1 回呼んで初回コストを払っておく。以降は挿入のたびに呼ぶ（状態が変わるためキャッシュ禁止） |

**ウォームアップの待ち方には区別がある。** `DictationSession.warmUp()` は
`AVAudioEngine` の起動（実測 327〜456 ms）と認識器の `prepare` は**待つ**（録音に必要なため）が、
**整形器の捨て推論と認識器の捨て往復は投げっぱなしにする。** 捨て推論はコールド時に
1.9〜3.3 秒掛かるので、これを待ってからホットキーを読み始めると**起動直後の数秒間、
押しても何も起きない**。整形は 1 発話目が温まる前に来ても生テキストへ縮退するだけで済むが、
ホットキーが効かないのは機能停止である。

**認識器の捨て往復**（`begin()` → `finish()` を 1 回通して捨てる）は、
`SpeechAnalyzer` の初回生成費用（実測 中央値 44〜64 ms / 最大 540 ms）を起動側へ移すために行う。
**`begin()` の復帰前に来たバッファは黙って捨てられるので、この費用は発話の頭の取りこぼしとして出る**
（詳細設計書 §10）。投げっぱなしにしても解析器が 2 つ同時に生きないよう、
**捨て往復は `finalizeTask` の枠へ入れて `startRecording()` の頭で待たせる**
（`SpeechModule` は 1 つの `SpeechAnalyzer` にしか装着できない。詳細設計書 §4.3.1）。

**`FoundationModels` は「セッションを温める」のではなく「デーモンを温める」。** モデルの常駐は
`LanguageModelSession` ではなくプロセス外のデーモン側にあり、セッションやプロセスの生存期間とは
独立している（`prewarm()` を一度も呼ばない新規プロセスでも 1 回目の `respond` が 0.376 秒だった）。
したがってセッションを常駐させる意味は無く、**発話ごとに作り直す**（実測 `init` 0.001〜0.002 秒、
再ロードは起きない）。使い回すと会話履歴が前の発話を次の整形へ持ち込む。詳細は
詳細設計書 §5.2。

**`LanguageModelSession.prewarm()` はロードを完了させない。** 実測で `prewarm()` が 0.013 秒で
返った後も 1 回目の `respond` に 3.318 秒掛かった。ロードを強いるのは `respond` の方なので、
起動時に捨て推論を 1 回通す。

**トレードオフ**: モデル常駐によりアイドル時メモリが増える。NFR-S3（150 MB 以下）を計測し、超過する場合は `.lingering` へ変更する（`SpeechAnalyzer` の `modelRetention` の話。`FoundationModels` 側はデーモンが管理するためアプリからは制御できない）。

## 7. エラー処理方針

原則: **発話を失わないことを最優先する。** 各段の失敗は上位の縮退動作で吸収し、最悪でもテキストをクリップボードに残す。

> **唯一の例外: secure input が有効な間は、挿入もクリップボードへの残置も行わない。**
>
> secure input が有効なのは**ユーザーがパスワードを入力しているとき**である。ここで原則どおり縮退すると、次が起きる。
>
> 1. 発話が LLM 整形（`FoundationModels`）へ渡る
> 2. **`history.json` へ平文で永続化される。** NFR-V2 が禁じているのは**音声**のディスク書き出しなので、テキスト履歴はこの禁止を素通りする
> 3. クリップボードへ残せば、パスワードがクリップボードに載る
>
> secure input は「この瞬間の入力を捕まえるな」という **OS からの明示的な合図**であり、それを迂回するのは機能ではなく欠陥である。**したがってこの場合に限り、発話を失うことを正とする。** 詳細設計書 §6.4。
>
> **この例外を「発話を失っている」と見て残置を足してはならない。** 足すとパスワードがクリップボードに載る。

| 発生箇所 | 失敗 | 縮退動作 | ユーザー通知 |
|---|---|---|---|
| 権限 | アクセシビリティ未許可 | 機能停止 | 設定画面へ誘導 |
| 権限 | マイク未許可 | 機能停止 | 設定画面へ誘導 |
| 設定 | **JSON を復元できない**（`settings.json` / `vocabulary.json` / `history.json`。手編集の書式誤り） | 既定値で動作する（起動はする） | **起動時と `--check` で、読めなかったファイル名を挙げて「既定値で動作しています」と告げる。** 黙ると症状だけが残る——設定なら「書き換えたのに効かない」、**辞書なら「固有名詞が直らない」**（FR-6 が無言で効かなくなる） |
| モデル | 日本語モデル未導入 | ダウンロード実行 | HUD に進捗表示 |

### 7.1 性能予算の配分（NFR-P6a / NFR-P6b）

**予算は分岐ごとに別である。** 要件定義書 §2.8.6 の裁定により、
1 秒（NFR-P6a）が守るのは「整形済みテキスト」ではなく「まず使えるテキスト」になった。

| 分岐 | NFR-P6a（1 秒）の内訳 | 整形の締め切り |
|---|---|---|
| **(a) 差し替え可能** | **M2 + 挿入** = 実測 45.1〜155.1 ms + 12〜34 ms = **57〜189 ms**（M2 の保守的な上限 199 ms で置くと 233 ms）。**整形は入らない** | **NFR-P6b**（目標 2 秒 / 打ち切り 3 秒。**どちらも推定値**。要件定義書 §4.2） |
| **(b) 差し替え不可** | **M2 + 整形の打ち切り + M4** = 199 + 750 + 50 = **999 ms**（従来と同じ計算。M2 は V-12 の修正後の保守的な上限。**旧定義では 177 + 750 + 50 = 977 ms だった**） | **既定 750 ms**（下記） |

**(a) の予算計算が「M2 が 199 ms、M4 が 50 ms なので整形に割ける上限は 751 ms」という形をしていないことに注意する。**
(a) では整形が予算の外に出るので、**整形の締め切りは 1 秒の予算から逆算されない。**
逆に **(a) では M2 が数百 ms 伸びても 1 秒に収まる**——これは持ち越し欠陥 V-12（末尾の欠落。
確定を待つ時間が伸びる）を直すときの余地でもある。

**整形のタイムアウトを既定 750 ms に設定する理由（(b) の分岐に限る）**: 超過時に待ち続けると
NFR-P6a（1 秒）を破るため、どこかで打ち切って生テキストを出す必要がある。その打ち切り位置は
**NFR-P4 の目標値（500 ms）ではなく、NFR-P6a の予算から逆算して決める。** 実測の最悪値で
M2 が 177 ms、M4 の予算が NFR-P5 の 50 ms なので、整形に割ける上限は 773 ms である。
**【フェーズ 2 で更新】V-12 の修正で M2 の定義が「解放 → 結果ストリームの終端」へ移り、
保守的な上限は 約 199 ms になった。整形に割ける上限は 751 ms で、既定 750 ms の余裕は
23 ms から 1 ms になった**（詳細設計書 §10）。

**当初は NFR-P4 と同じ 500 ms にしていたが、Task 10 の M5（現 M5a）実測でそれが高過ぎる代償を
払っていることが判った**（負荷下で 10 発話中 4 発話が整形されずに終わり、しかも超過分は
501〜527 ms とわずかだった）。目標値と打ち切り位置を同じ数にしていたのが誤りで、
**目標は「これくらいで終わってほしい」、打ち切りは「待つより生テキストの方がましになる境界」**
という別の概念である。詳細設計書 §10。

**ただしマージンは薄い。「実測に対し妥当な余裕がある」とは言えない。** Task 6 の実測
（`refine()` 全体・10 サンプル）では、低負荷で中央値 0.389 秒 / 最大 0.413 秒（500ms 超 0 件）だが、
**機体が並行して他の処理をしている条件では中央値 0.461 秒 / 最大 0.518 秒で、500ms 超が 1/10 出た。**
負荷下の余裕は 39 ms しかない。超えた発話は整形されず生テキストのまま挿入される
（壊れはしないが FR-5 が効かない）。

**この余裕の薄さが、打ち切りを 750 ms へ引き上げた理由である**（上記）。Task 10 が
`DictationSession` 越しに M5 を 2 条件で実測し、打ち切り 500 ms では負荷下で
10 発話中 4 発話が整形されずに終わることを確かめた。詳細設計書 §10。

> **750 ms でも足りない（2026-08-14 / 実機の肉声）。** 上の実測はすべて**3 秒の発話**で
> 行っており、**入力が長ければ生成も長くかかる**という依存を条件に含めていなかった。
> 実機の履歴 11 件では、**40 字以上の 8 件がすべて打ち切られて生テキストへ縮退した**
> （効いたのは 18 字以下の 3 件だけ。実測の 1 件は `refine 791 ms`）。
> **FR-5 は実運用の発話長では機能していない。**
>
> **打ち切りを延ばすだけでは解けない。** NFR-P6（当時の定義。1 秒。現 NFR-P6a）の予算が先に尽きる
> （実測 1142 ms で既に超過）。要件定義書 §2.8.4。
>
> **→ 裁定は要件定義書 §2.8.6。** 打ち切りを延ばすのではなく、**整形を挿入の前提から外した。**
> 差し替えできる挿入先では生テキストを先に挿入し、整形は NFR-P6b の下で後から反映する。
> **750 ms という値そのものは (b) の分岐の打ち切りとして残る**（上の予算計算は (b) では変わらないため）。

### 7.2 差し替え（FR-5(a) / FR-7）が失敗したときに何が残るか

**1 行を除いて、失敗の結末はすべて「生テキストが欄にある」である。**
これは**現行の実装の正常系と同じ状態**であり、この設計は「うまくいけば良くなる／失敗すれば現状のまま」という形をしている。

| 失敗 | 挿入先の欄 | クリップボード | 履歴 | 重さ |
|---|---|---|---|---|
| 整形が NFR-P6b の打ち切りに掛かる | **生テキスト** | 触らない | raw | 軽（整形が効かないだけ） |
| 整形が逸脱して `RefinementGuard` に落ちる | **生テキスト** | 触らない | raw | 軽 |
| 差し替えの条件（C-1〜C-7）が揃わない | **生テキスト** | 触らない | raw + refined | 軽 |
| 事前検査が不一致（利用者が編集した / カーソルが動いた） | **生テキスト** | 触らない | raw + refined | 軽 |
| 範囲設定・書き込みが `AXError` | **生テキスト** | 触らない | raw + refined | 軽 |
| 差し替えが無言失敗（R-4 と同じ形。何も起きていない） | **生テキスト** | 触らない | raw + refined | 軽 |
| 次の発話が始まって差し替えを破棄 / 終了で破棄 | **生テキスト** | 触らない | raw + refined | 軽 |
| **事後検査が喪失を示す（R-9）** | **不明** | **整形結果を残す** | raw + refined | **重い。ただし検知済み・告知済み・写しが 2 つある。以後そのアプリでは試さない** |
| secure input（差し替えの直前に有効化されていた） | 生テキスト（挿入時点では有効でなかった） | 残さない | 残さない | **意図された例外** |

**R-9 の行に対して 2 度目の書き込みはしない。** 二重に入るのは入らないことより悪い（詳細設計書 §6.2 の裁定と同じ）。
**ここでクリップボードを奪うのは、§6.3 の「送出に失敗したときは復元しない」と同じ取引である**
——「クリップボードを壊さない」を捨てて「発話を失わない」を取る。**ただし喪失を検知できたときに限る。**

## 8. UI 設計

### 8.1 HUD の配置

- 表示先は**常に内蔵ディスプレイ**（FR-3）。外部ディスプレイで作業中も内蔵側に表示する。
- **内蔵ディスプレイの判定は `CGDisplayIsBuiltin` で行う。** 実測で内蔵 = 1 / 外部 = 0 を返した（2026-08-14 / MacBook Pro Mac15,3 / M3 / macOS 26.5.2 / 内蔵 + DELL S2722QC の 2 画面）。詳細設計書 §7.1。
- **その画面に notch があるかは別の問い**であり、`auxiliaryTopLeftArea` / `auxiliaryTopRightArea` が非 nil かで判定する（表示形状の分岐に使う）。
- ウィンドウレベルは全画面表示アプリとメニューバーより上に出す必要がある。**`.statusBar + 1`（= 26）を採る**（z 順の実測は詳細設計書 §7.2）。
- `NSPanel` を `.borderless` + `.nonactivatingPanel` で構成し、フォーカスを奪わない。
- **HUD の window は `NSApp.run()` が始まった後にだけ生成・表示する**（実測。下記）。

> **以前の記述（`safeAreaInsets.top > 0` で判定し、該当がなければ `NSScreen.screens.first` へフォールバックする）は誤りだったので取り消した。**
> この機体ではたまたま正しい答えを出すが、**notch 非搭載の MacBook では内蔵でも `safeAreaInsets.top == 0` になる**ため内蔵を内蔵と認識できない。
> また `NSScreen.screens.first` は主ディスプレイであって内蔵とは限らない（実測でも `NSScreen.main != NSScreen.screens.first` だった）。

> **フォーカスを奪わないことは必須要件である。** 挿入先アプリのフォーカスが外れると、テキストの挿入先が失われる。
>
> **`NSApp.run()` の前に window を `orderFrontRegardless()` すると、AppKit が `finishLaunching` の時点でアプリを活性化する**（実測）。
> `setActivationPolicy(.accessory)` を先に呼んでいても、`.nonactivatingPanel` でも、`canBecomeKey == false` でも防げない。
> 活性化すると `AccessibilityInserter.frontmostProcessIdentifier()` が拾う最前面 pid が Ghost Voice 自身になり、**挿入先が壊れる。**
> したがって「起動時に非表示の HUD を用意しておく」実装にしてはならない。詳細設計書 §7.2。

### 8.1.1 内蔵ディスプレイが存在しない構成（クラムシェル）

蓋を閉じて外部ディスプレイだけで使う場合、内蔵は `NSScreen.screens` から消えるため `CGDisplayIsBuiltin` の該当は無くなる（**この状態の実測は未実施。V-22**）。
FR-3 は物理的に満たせないので、要件定義書 §4.3 の「notch 非搭載機ではフォールバック表示」と同じ扱いにする。

**採る形を決めた（2026-08-15 / トラック C）: 主ディスプレイの「メニューバーの直下」（`visibleFrame.maxY`）へ、notch のときと同じ帯を出す。**

当初の候補は (a) 主ディスプレイのメニューバー**右端付近**、(b) HUD を出さずメニューバーアイコンの状態変化だけ、の 2 つだった。**どちらも採らなかった。**

- **(b) を採らない理由**: このアプリは**メニューバー項目をまだ 1 つも持たない**（`Sources/GhostVoiceApp/Shell/` に `NSStatusItem` は無い）。(b) は「状態変化だけにする」ための表示先が存在しないので、実際には「何も出さない」になる。**録音中かどうかを知る手段が消える。**
- **(a) の「右端付近」を採らない理由**: メニューバーの右端には**コントロールセンター等のステータス項目が layer 25 に居る**（実測）。HUD は layer 26 なので、重ねればそれを隠す。**メニューバーの下端（`visibleFrame.maxY`）より下に置けば、何も隠さずに済む。**
- **同じ形にした理由**: notch 機のフォールバック（notch 非搭載の内蔵機）と、内蔵が無い構成とで、置き方を分ける必要が無い。**分けると、どちらも実測できないまま 2 通りの未検証の経路が増える。**

**FR-3 を果たせていないことは表に出す。** 内蔵へ出せなかったときは起動時の診断に 1 行出す（`HUDPlacement.isOnBuiltInDisplay`）。黙って外部へ出すと、出ていること自体が誤りに見える。

> **この決定は未実測の上に立っている（V-22）。** 蓋を閉じたときの `NSScreen.screens` の中身は確かめていない。
> 確かめる手順は [README](../README.md) の「HUD の目視確認（`--hud-check`）」にある。

### 8.2 表示内容

| 状態 | 表示 |
|---|---|
| `idle` | 非表示 |
| `recording` | 録音インジケータ（音量連動）＋ 現在の言語（日/EN）＋ 暫定テキスト（末尾 2 行程度） |
| `finalizing` / `refining` | 処理中インジケータ |
| `revising` | **控えめに出す。** 挿入は既に終わっており、利用者は次の作業へ移っている。整形の反映に失敗した場合だけ明示的に告げる（§7 の縮退表） |
| `inserting` → 完了 | チェックマークを短時間表示して収納 |
| エラー | エラー内容を数秒表示 |

**`.failed` の直後には必ず `.idle` が続く**（`DictationSession.fail()` が同期で両方を emit する）。したがって**表示の保持時間は HUD 側が持つ**——状態をそのまま描く実装ではエラーが 1 フレームも見えない（詳細設計書 §7.4）。

**暫定テキストは `.volatile` 更新のたびに届く**（長い発話では数百件）。**メインスレッドを塞ぐと `CGEventTap` の配送が p50 0.045 ms → 12.8 ms へ悪化する**（ランループ検証の実測）ので、HUD は録音中の中身の更新を間引く。**間引くのは中身だけで、状態の変わり目は間引かない**（詳細設計書 §7.4）。

### 8.3 notch UI の実装方式

| 案 | 内容 | 判断 |
|---|---|---|
| A | [DynamicNotchKit](https://github.com/MrKai77/DynamicNotchKit)（MIT / macOS 13+ / 活発）を採用 | **不採用**（2026-08-14 に裁定） |
| B | `NSPanel` を自前実装 | **採用** |

**当初は案 A を採っていたが、案 B へ改めた。** 理由は次のとおり。

1. **案 B の難所とされた 2 点は、どちらも実測で解決した**（2026-08-14 / M3 / macOS 26.5.2）。
   内蔵ディスプレイの特定は `CGDisplayIsBuiltin`（§8.1）、フォーカスを奪わないことは
   `.borderless` + `.nonactivatingPanel` + `orderFrontRegardless()`（詳細設計書 §7.2）で成立することを確かめた。
2. **残る差は形状（notch の角丸との連続）と展開アニメーションだけ**であり、これは機能要件ではない。
3. 案 B は **FR-3（表示先を内蔵へ固定する）を完全に制御できる。** 他人の実装の都合に縛られない。
4. **外部依存ゼロを維持できる**（§1 の方針 2）。

**V-5（DynamicNotchKit が FR-3 に対応するか）は「採用しないため問わない」として閉じた。**

| `timestamp` | 発話日時 |
| `rawText` | 生テキスト（Undo 用、FR-7） |

> **アクセシビリティ・入力監視・キー送出には、`Info.plist` に書けるキーが存在しない**（実測 2026-08-14）。
> macOS の TCC 本体（`/System/Library/PrivateFrameworks/TCC.framework/Support/tccd`）が参照する
> `NS…UsageDescription` キーを列挙したところ、`kTCCServiceAccessibility` / `kTCCServiceListenEvent` /
> `kTCCServicePostEvent` に対応するキーは 1 つも無かった（`NSMicrophoneUsageDescription` は存在する）。
> これら 3 つは「アプリが説明文を出す」形式ではなく、**利用者がシステム設定で明示的に追加する形式**である。
> `NSAccessibilityUsageDescription` のような名前を書いても**無視されるだけ**なので書かない。
>
> **`NSAppleEventsUsageDescription` も書かない。** Ghost Voice は Apple Events でアプリを操作しない
> （挿入は AX API と `CGEvent.post`。詳細設計書 §6）。書くと無関係なダイアログの余地を作るだけである。

> **なぜ ad-hoc 署名を採らないか（実測 2026-08-14 / M3 / macOS 26.5.2 / Xcode 26.6）。**
> ad-hoc 署名の designated requirement（DR）は既定で **`cdhash` 単体**であり、identifier もチーム ID も入らない。
> `codesign` 自体は決定的だが（同じ入力なら同じ cdhash）、**実コードを 1 箇所変えて再ビルドすると cdhash は別物になる**
> （`Info.plist` の `CFBundleVersion` を 1 つ上げるだけでも変わった）。TCC の許可は DR に紐づくので、
> ad-hoc のままだと**ビルドのたびに 4 つの権限を付け直させる**設計になる。
> Apple Development 証明書で署名すると DR は
> `identifier "…" and anchor apple generic and certificate leaf[subject.CN] = "…"` の形になり、
> **実コードを変えて再ビルドしても DR の文字列は 1 文字も変わらなかった**（cdhash は変わる）。
> 実在アプリ（VS Code / Chrome / Calculator）の DR にも cdhash は入っていない。
> **ただし「証明書署名なら再ビルド後も TCC の許可が実際に残る」ことは未実測である（V-16）。** 許可の付与が要るため。
>
> **`CFBundleIdentifier` は一度決めたら変えない。** DR に焼き込まれるので、変えると許可がすべて失われ、
> システム設定の一覧に古い項目が残る。

> **`.xcodeproj` を作らない理由。** `project.pbxproj` は差分が読めず競合の温床で、正本＝ドキュメントという本プロジェクトの規律と噛み合わない。
> ビルド構成が Xcode の GUI へ散ると、上の表と実物の対応が取れなくなる。
> また `swift package generate-xcodeproj` は既に存在しない（実測）ので、作るなら手で保守することになる。
> SwiftUI の `@main struct App`（`MenuBarExtra` / `Settings` を含む）が `swift build` だけで通ること、
> `View` を含むライブラリとテストターゲットを同居させても `swift test` が影響を受けないことは実測済みである（2026-08-14）。

### 10.1 フェーズ 1 の許可は `.app` へ引き継がれない（実測 2026-08-14）

同一の `.app` を「ターミナルから直接実行」と「`open` で起動（LaunchServices）」の 2 通りで走らせ、**照会だけ**を行った
（要求系 API は呼ばず、ダイアログは 1 つも出していない）。

| 照会項目 | ターミナルから直接実行 | `open` で起動 |
|---|---|---|
| `AVCaptureDevice.authorizationStatus(for: .audio)` | `.authorized` | **`.notDetermined`** |
| `AXIsProcessTrusted()` | true | **false** |
| `CGPreflightListenEventAccess()` | true | **false** |
| `CGPreflightPostEventAccess()` | true | **false** |
| `getppid()` | ターミナル | **1（launchd）** |

→ **`.app` は Finder / Dock / `open` から起動された瞬間に自分自身が責任プロセスになり、ターミナルアプリの許可を一切引き継がない。**
したがって**フェーズ 2 では 4 つの権限を Ghost Voice.app に対して付け直してもらう必要がある**（FR-10。詳細設計書 §9）。これは避けられない。

**手順書には「ターミナルから `Ghost Voice.app/Contents/MacOS/…` を直接叩かないこと」を書く。**
叩くとターミナルの許可を引き継いでしまい、「動いているのに Finder から起動すると動かない」という切り分け不能な状態になる。

> `AXUIElement` 系 API は `kTCCServiceAccessibility`、`CGEvent.post` は `kTCCServicePostEvent`、`CGEvent.tapCreate`（ホットキー）は `kTCCServiceListenEvent` という**それぞれ別の TCC サービス**を使う。前 2 つは「システム設定 > プライバシーとセキュリティ > アクセシビリティ」に、`kTCCServiceListenEvent` は「入力監視」に表示されるが、内部的にはいずれも別枠である。二段構えの挿入（§5.2）は前 2 つを、ホットキー監視は 3 つ目を必要とする。
>
> **どれか 1 つを他の判定に流用してはならない。** 片方だけ許可された状態は原理的にありうるため、値が一致する機体では取り違えに気付けない（詳細設計書 §2.2 / §6.2）。
>
> **したがって照会の実装は 1 つだけにする。** サービスと API の対応表は
> `Sources/GhostVoiceCore/Support/PermissionInquiry.swift` の `PermissionProbes.system` にだけ置き、
> CLI も `.app` もそこを通す。**2 実装あると、この規律が片方だけ守られている状態を作れてしまう。**

## 12. テスト方針

| 層 | 対象 | 方法 |
|---|---|---|
| 単体 | `Refiner`, `Vocabulary`, `HistoryStore`, `SettingsStore` | GhostVoiceCore の XCTest。外部依存はモック |
| 単体 | **`TextReplacer`（差し替え / Undo）** | 代役の AX で「成功したが何も変わらない」「`AXError`」「読み戻しが不一致」を作り、**⌫ / ⌘V の追撃が 0 回であること**と**生テキストが残ること**を確かめる |
| 単体 | **NFR-V3 の例外の 4 条件** | **読み取りの範囲が「直前に自分が書き込んだ範囲」と一致すること**を検査で固定する。範囲が広がる変更・読んだ値を保持する変更・不一致の内容を見る変更が入ったら落ちること（要件定義書 §4.2 の 4 条件 / 詳細設計書 §8.3） |
| 単体 | `TranscriptionEngine` | 音声ファイルを入力とするゴールデンテスト。既知の音声に対する認識結果を回帰確認する |
| 結合 | 挿入経路 | 主要アプリ（Slack / Chrome / Xcode / Notion / ターミナル）での手動確認（V-3） |
| 性能 | NFR-P1〜P6 | 各段に計測点を置き、履歴とともにログ出力する |

**ゴールデンテスト用の音声資産は `say` コマンドで再生成可能にする。** 本設計の調査で用いた 103 秒の日本語音声がそのまま使える。
