## 1. 設計方針

| # | 方針 | 理由 |
|---|---|---|
| 1 | コアロジックを Swift Package に分離し、アプリは UI と OS 統合のみを担う | NFR-M2（テスト容易性）、NFR-M3（OSS 公開） |
| 2 | 外部依存を最小化する。導入するのは notch UI ライブラリのみ | 条件 C-2（軽量）、OSS 公開時の可読性 |
| 3 | 認識・整形・挿入の各段をプロトコルで抽象化する | NFR-M1（差し替え可能）、R-2 / R-4 への対応 |
| 4 | 失敗時は必ず縮退動作を持たせ、発話を失わない（**例外は secure input 中のみ**。§7） | 音声は再現できないため。R-4 / R-5 |
| 5 | 常時起動しておくべきものは起動時に温めておく | NFR-P1 / NFR-P4。コールドスタートは実測 1.906 秒（設計調査）／ 3.318 秒（Task 6）。**`FoundationModels` は捨て推論を通さないと温まらない**（§6） |

## 4. 状態遷移

```
                    ┌──────────┐
          ┌────────▶│   idle   │◀───────────┐
          │         └────┬─────┘            │
          │              │ キー押下          │
          │              ▼                  │
          │        ┌──────────┐             │
          │        │recording │             │ 完了 / 中断
          │        └────┬─────┘             │
          │             │ キー解放           │
          │             ▼                   │
          │       ┌───────────┐             │
          │       │finalizing │             │
          │       └─────┬─────┘             │
          │             │ 確定テキスト取得    │
          │             ▼                   │
          │       ┌───────────┐             │
    生テキスト     │ refining  │             │
    で縮退  └──────┴─────┬─────┘             │
                        │ 整形完了           │
                        ▼                   │
                  ┌───────────┐             │
                  │ inserting │─────────────┘
                  └───────────┘
```

| 状態 | HUD 表示 | 主な処理 |
|---|---|---|
| `idle` | 非表示（notch のまま） | 待機。AudioEngine は `start()` 済みで保持。**LLM セッションは保持しない**（温まっているのはデーモン側のモデル。§6） |
| `recording` | 展開＋音量インジケータ＋暫定テキスト | 音声取得と逐次認識 |
| `finalizing` | 「確定中」 | `finalizeAndFinishThroughEndOfInput()` |
| `refining` | 「整形中」 | LLM 整形。既定 750 ms を超えたら生テキストで縮退（§7） |
| `inserting` | 「挿入中」→ 完了表示 | AX 挿入、失敗時 Pasteboard フォールバック |

**中断（ESC 押下）は、挿入が始まる前のどの状態からでも `idle` へ戻る。** 中断時、録音済み内容は破棄せず履歴に残す（発話を失わないため）。挿入していないので `insertionMethod` は **`.notInserted`** で記録する（`.clipboardOnly` で記録すると「クリップボードに残っている」という嘘になる）。整形は経ていないので `refinedText` は nil であり、Undo の対象にはならない。

> **ただし挿入を始めた後の ESC は受け付けない。** `inserter.insert(_:)` を呼んだ後に中断すると、⌘V を送出済みのままクリップボードの復元だけが走り、**テキストがどこにも残らない**（詳細設計書 §6.3 が潰した欠陥と同じ形）。**「中断が効かない」より「テキストが消える」ほうが重い**ので、ここは手遅れとして扱い完走させる。
>
> したがって中断が効くのは `recording` / `finalizing` / `refining` の 3 状態である。処理窓は実測 400〜800 ms あり、人が ESC を押すのに十分な長さがあるため、**録音中だけに限ってはならない**（限ると、ユーザーが「挿入するな」と押したのに挿入される）。

> **例外が 1 つある。処理中に PTT の押下が先着していると、その後の ESC は処理中の発話には届かない。** `run()` は `.pressed` を受けた時点で次の発話の準備に入り、そこで前の発話の完了を待つため、後続の `.cancelled` は処理が終わるまで配送されない。
>
> **ただし ESC が捨てられるわけではない。** 配送された時点では次の発話が録音中なので、**そちらが中断される**（実測で確認済み。`cancelAfterQueuedPressAppliesToNextUtterance` が固定している）。ユーザーは PTT を押し直して新しい発話を始めた後に ESC を押しており、「新しい方を止める」は読みとして妥当である。
>
> **塞がないことを選んだ。** 塞ぐには押下の経路も非同期にする必要があり、そうすると「押下は前の発話の完了を待ってから始める」という直列性——ESC を届かせるためにイベントループから外へ動かした、まさにその性質——を作り直すことになる。得られるのは「ESC の宛先が古い方に変わる」だけで、失う可能性のあるものは発話の取りこぼしである。**割に合わない。**

> **ここにも secure input の例外が及ぶ。** 「履歴に残す」は挿入経路を通らないので、§7 の例外を挿入側だけに実装すると**この経路からパスワードが `history.json` へ入る**。中断時も secure input が有効なら履歴へ残してはならない。

### 4.1 実装上の要点（`DictationSession`）

`Sources/GhostVoiceCore/Session/DictationSession.swift`。以下はいずれも実測に裏づけられている。

| # | 決めたこと | 理由 |
|---|---|---|
| 1 | **`begin()` を待ってからタップを張る** | `feed` は `begin()` 復帰前のバッファを黙って捨てる。逆順にすると**発話の頭が落ちる**（詳細設計書 §4.4）。`begin()` は実測 1.2〜1.4 ms なので待つ費用は小さい |
| 2 | **`stopTap()` → 供給タスクの完走 → `finish()` の順** | `removeTap` は端数バッファを配ってから返り、リサンプラは 231 フレーム（14.4 ms）を抱える。供給しきる前に `finish()` を撃つと解析器の入力はもう閉じており、**発話の末尾が落ちる**（詳細設計書 §3.4） |
| 3 | **整形は `.final` の到着で始める。`finish()` の復帰を待たない** | `.final` は `finish()` の復帰より実測 5〜48 ms 早く届く。復帰を待つと毎発話でそのぶんを捨てる（詳細設計書 §10 の M2） |
| 4 | **キー解放より前の `.final` では先へ進まない** | 長い発話では録音中にも確定が出る。これで進むと発話の後半を失う |
| 5 | **確定に締め切りを置く**（`finalizeDeadline`、既定 2 秒） | 認識器が黙り込んだときに録音が終わらなくなるのを防ぐ。締め切りに達したら暫定テキストへ縮退する（空で捨てるよりは残す） |
| 6 | **最大録音時間**（`maxRecordingDuration`、既定 120 秒） | 混在入力源で解放を取りこぼす経路が残っている（詳細設計書 §2.3）。時間で抜ける道が要る。到達時は**中断ではなく確定**として扱う |
| 7 | **secure input は整形の手前でも見る** | 挿入時にしか見ないと、拒否する頃には発話が既に `FoundationModels` を通っている（§7 が挙げる害の 1 番目）。手前で弾けば整形にも履歴にもクリップボードにも渡らない |
| 8 | **確定〜挿入をキャンセルの効かないタスクで走らせる** | 下記 |
| 8b | **`run()` のイベントループは確定〜挿入を待たない** | 待つと処理中（実測 400〜800 ms）に届いた ESC がイベント列に溜まり、**中断が原理的に効かなくなる**。発話の直列性は次の押下側（`startRecording()` の頭）で待って保つ |
| 9 | **起動時、整形器の捨て推論は待たない** | `prewarm()` はコールド時に実測 1.9〜3.3 秒掛かる。待ってからホットキーを読み始めると**起動直後の数秒間、押しても何も起きない**（§6） |
| 10 | **認識器の `prepare` を発話ごとに呼び直さない** | `reserve` の後に失敗した `prepare` はロケール枠（上限 5）を解放しない。毎発話で再試行を重ねると `localeReservationLimitReached` に達して回復不能になる。ロケール変更は `prepareTranscriber(locale:kind:)` を明示的に呼ぶ形にし、**再試行の回数を人の操作の回数に縛る** |

> **8 について。** キャンセルされたタスクの中では `AsyncStream` の `next()` が即座に nil を返す（実測）。確定から挿入までをそういう文脈で走らせると、次が同時に起きる。
>
> - 供給の待ち合わせが即座に抜け、**発話の末尾が認識器へ届かない**
> - `withTimeout` が常に nil を返し、**整形が必ず縮退する**
> - `PasteboardInserter` の復元待ち（120 ms）が 0 になり、**⌘V が処理される前にクリップボードが戻って発話が消える**（詳細設計書 §6.3 が潰した欠陥の再発）
>
> これは机上の話ではなく、**最大録音時間の満了で確定へ入る経路が実際にこれを踏んでいた**（その経路の呼び出し元は、確定処理の入口で `cancel()` される当のタスク自身である）。アプリ終了時に処理中の発話を巻き添えにする経路も同じ形になる。非構造化タスク（`Task {}`）はキャンセルを継承せず、`Task<Void, Never>` の `value` は待つ側がキャンセルされても早く返らないので、そこへ逃がして直列性ごと守る。

### 5.2 テキスト挿入の二段構え（R-4 対策）

**入口で secure input を確かめる。** 有効ならどの経路も試さず、クリップボードにも残さず拒否する（ユーザーがパスワードを入力しているため。詳細設計書 §6.4）。

```
                  ┌─────────────────────────┐
                  │ secure input が有効か？   │
                  └───────────┬─────────────┘
                              │
                     無効 ◀───┴───▶ 有効 → 拒否（何も残さない）
                              │
                  ┌───────────▼─────────────┐
                  │ フォーカス要素を AX 取得  │
                  └───────────┬─────────────┘
                              │
                   取得成功 ◀─┴─▶ 取得失敗
                      │              │
                      ▼              │
        ┌──────────────────────────┐ │
        │ kAXSelectedText へ書込    │ │
        └───────────┬──────────────┘ │
                    │                │
    ステータス成功 ◀─┴─▶ 失敗 ───────┤
            │                        │
            ▼                        ▼
         ┌──────┐      ┌──────────────────────────┐
         │ 完了 │      │ Pasteboard 退避           │
         └──────┘      │ → テキスト設定 → ⌘V 送出  │
                       │ → Pasteboard 復元         │
                       └───────────┬──────────────┘
                                   │
                        成功 ◀─────┴─────▶ 失敗
                          │                 │
                          ▼                 ▼
                       ┌──────┐   ┌────────────────────┐
                       │ 完了 │   │ 履歴に退避し HUD で  │
                       └──────┘   │「コピー済み」と通知  │
                                  └────────────────────┘
```

**AX 段の「失敗」は `AXUIElementSetAttributeValue` のステータスのみで判定する。** 書き込み後の読み戻しはしない（理由と残余リスクは詳細設計書 §6.2）。したがって**AX が成功を返しながら何も入らなかった場合は検出できず、フォールバックは走らない。**

**Pasteboard の退避と復元は必須。** ユーザーのクリップボードを破壊してはならない。復元は ⌘V の送出完了を待ってから行う。ただし**送出そのものができなかった場合は復元しない**（テキストを残す方を選ぶ。詳細設計書 §6.3）。

## 6. ウォームアップ設計

実測により、初回コストが体感を大きく損なうことが判明している。

| 対象 | コールド | ウォーム | 対策 |
|---|---|---|---|
| `FoundationModels` | 1.906 秒（設計調査）／ 3.318 秒（Task 6） | **低負荷 0.389 秒 / 負荷下 0.461 秒**（中央値。最大 0.413 / 0.518 秒） | アプリ起動時に**捨て推論を 1 回通す**。`prewarm()` を呼ぶだけでは足りない。**セッションは常駐させず発話ごとに作る**（下記） |
| `AVAudioEngine` | **実測 327 ms（アイドル）／ 456 ms（CPU 負荷下）** | タップ着脱は**実測 0.07〜0.6 ms** | 起動時から `start()` 済みにし、録音開始時はタップの着脱のみ行う。**マイク未許可のまま `inputNode` に触れると実測 510 秒ブロックする**ため、`prepare()` は権限を先に確かめる（詳細設計書 §3.3） |
| `SpeechAnalyzer` | モデルロードあり | — | `prepareToAnalyze(in:)` を事前実行。`Options.modelRetention` に `.processLifetime` を指定しモデルを常駐させる |
| `CGPreflightPostEventAccess()`（キー送出の権限照会） | **実測 初回 16.7 ms** | 以降も **毎回 10.6 ms**（キャッシュされない） | 起動時に `PostEventAuthorization.shared.refresh()` を 1 回通し、以後は保持値を読む。**この API は他と違いウォームアップでは安くならない**ので、キャッシュ側で解決する（詳細設計書 §9） |
| `IsSecureEventInputEnabled()` | **実測 初回 23.8 ms** | **0.000 ms** | 起動時に 1 回呼んで初回コストを払っておく。以降は挿入のたびに呼ぶ（状態が変わるためキャッシュ禁止） |

**ウォームアップの待ち方には区別がある。** `DictationSession.warmUp()` は
`AVAudioEngine` の起動（実測 327〜456 ms）と認識器の `prepare` は**待つ**（録音に必要なため）が、
**整形器の捨て推論は投げっぱなしにする。** コールド時に 1.9〜3.3 秒掛かるので、これを待ってから
ホットキーを読み始めると**起動直後の数秒間、押しても何も起きない**。整形は 1 発話目が
温まる前に来ても生テキストへ縮退するだけで済むが、ホットキーが効かないのは機能停止である。

**`FoundationModels` は「セッションを温める」のではなく「デーモンを温める」。** モデルの常駐は
`LanguageModelSession` ではなくプロセス外のデーモン側にあり、セッションやプロセスの生存期間とは
独立している（`prewarm()` を一度も呼ばない新規プロセスでも 1 回目の `respond` が 0.376 秒だった）。
したがってセッションを常駐させる意味は無く、**発話ごとに作り直す**（実測 `init` 0.001〜0.002 秒、
再ロードは起きない）。使い回すと会話履歴が前の発話を次の整形へ持ち込む。詳細は
詳細設計書 §5.2。

**`LanguageModelSession.prewarm()` はロードを完了させない。** 実測で `prewarm()` が 0.013 秒で
返った後も 1 回目の `respond` に 3.318 秒掛かった。ロードを強いるのは `respond` の方なので、
起動時に捨て推論を 1 回通す。

**トレードオフ**: モデル常駐によりアイドル時メモリが増える。NFR-S3（150 MB 以下）を計測し、超過する場合は `.lingering` へ変更する（`SpeechAnalyzer` の `modelRetention` の話。`FoundationModels` 側はデーモンが管理するためアプリからは制御できない）。

## 7. エラー処理方針

原則: **発話を失わないことを最優先する。** 各段の失敗は上位の縮退動作で吸収し、最悪でもテキストをクリップボードに残す。

> **唯一の例外: secure input が有効な間は、挿入もクリップボードへの残置も行わない。**
>
> secure input が有効なのは**ユーザーがパスワードを入力しているとき**である。ここで原則どおり縮退すると、次が起きる。
>
> 1. 発話が LLM 整形（`FoundationModels`）へ渡る
> 2. **`history.json` へ平文で永続化される。** NFR-V2 が禁じているのは**音声**のディスク書き出しなので、テキスト履歴はこの禁止を素通りする
> 3. クリップボードへ残せば、パスワードがクリップボードに載る
>
> secure input は「この瞬間の入力を捕まえるな」という **OS からの明示的な合図**であり、それを迂回するのは機能ではなく欠陥である。**したがってこの場合に限り、発話を失うことを正とする。** 詳細設計書 §6.4。
>
> **この例外を「発話を失っている」と見て残置を足してはならない。** 足すとパスワードがクリップボードに載る。

| 発生箇所 | 失敗 | 縮退動作 | ユーザー通知 |
|---|---|---|---|
| 権限 | アクセシビリティ未許可 | 機能停止 | 設定画面へ誘導 |
| 権限 | マイク未許可 | 機能停止 | 設定画面へ誘導 |
| 設定 | **JSON を復元できない**（`settings.json` / `vocabulary.json` / `history.json`。手編集の書式誤り） | 既定値で動作する（起動はする） | **起動時と `--check` で、読めなかったファイル名を挙げて「既定値で動作しています」と告げる。** 黙ると症状だけが残る——設定なら「書き換えたのに効かない」、**辞書なら「固有名詞が直らない」**（FR-6 が無言で効かなくなる） |
| モデル | 日本語モデル未導入 | ダウンロード実行 | HUD に進捗表示 |
| 認識 | 無音・認識結果ゼロ | 何もせず `idle` へ | HUD に「認識できませんでした」 |
| 整形 | Apple Intelligence 無効 | 生テキストを挿入 | HUD に「整形なし」バッジ |
| 整形 | 打ち切り超過（既定 750 ms） | 生テキストを挿入 | 同上 |
| 整形 | 生成エラー | 生テキストを挿入 | 同上 |
| 挿入 | AX 失敗 | Pasteboard フォールバック | なし（透過的） |
| 挿入 | 両方失敗 | クリップボードへ格納し履歴に保存 | HUD に「コピーしました」 |
| 認識 | 確定が締め切り（既定 2 秒）内に来ない | 暫定テキストを整形・挿入へ回す | なし |
| 録音 | 最大録音時間（既定 120 秒）に到達 | **中断ではなく確定**として扱い、そこまでの発話を挿入する | なし |
| 中断 | ESC による中断 | 挿入しない。**履歴には `.notInserted` として残す**（§4） | HUD を収納 |
| 監視 | **キーイベントのタップが無効化された**（応答遅延 / 無効化要求）。録音中なら解放を取りこぼす | **中断ではなく確定**として扱い、そこまでの発話を挿入する（最大録音時間の満了と同じ裁定。**利用者は喋っていたのであって中断を要求していない**） | CLI が「監視が停止した。起動し直せ」を出す |
| 履歴 | **`history.json` へ書けない**（容量・権限・破損ファイルの退避に失敗） | **握り潰さない。** 挿入済みなら失うのは履歴と Undo だけ、**中断された発話は写しがそこにしか無いので失われる**。どちらかを利用者へ告げる | CLI が `[エラー] 履歴に保存できませんでした…` を出す（文言は挿入済みかどうかで変える） |
| 挿入 | **secure input が有効** | **何もしない。挿入もクリップボードへの残置も履歴への保存もしない**（上記の例外） | HUD に「パスワード入力中は挿入しません」（フェーズ 2） |

**整形のタイムアウトを既定 750 ms に設定する理由**: 超過時に待ち続けると NFR-P6
（合計 1 秒以内）を破るため、どこかで打ち切って生テキストを出す必要がある。その打ち切り位置は
**NFR-P4 の目標値（500 ms）ではなく、NFR-P6 の予算から逆算して決める。** 実測の最悪値で
M2 が 177 ms、M4 の予算が NFR-P5 の 50 ms なので、整形に割ける上限は 773 ms である。

**当初は NFR-P4 と同じ 500 ms にしていたが、Task 10 の M5 実測でそれが高過ぎる代償を
払っていることが判った**（負荷下で 10 発話中 4 発話が整形されずに終わり、しかも超過分は
501〜527 ms とわずかだった）。目標値と打ち切り位置を同じ数にしていたのが誤りで、
**目標は「これくらいで終わってほしい」、打ち切りは「待つより生テキストの方がましになる境界」**
という別の概念である。詳細設計書 §10。

**ただしマージンは薄い。「実測に対し妥当な余裕がある」とは言えない。** Task 6 の実測
（`refine()` 全体・10 サンプル）では、低負荷で中央値 0.389 秒 / 最大 0.413 秒（500ms 超 0 件）だが、
**機体が並行して他の処理をしている条件では中央値 0.461 秒 / 最大 0.518 秒で、500ms 超が 1/10 出た。**
負荷下の余裕は 39 ms しかない。超えた発話は整形されず生テキストのまま挿入される
（壊れはしないが FR-5 が効かない）。

**この余裕の薄さが、打ち切りを 750 ms へ引き上げた理由である**（上記）。Task 10 が
`DictationSession` 越しに M5 を 2 条件で実測し、打ち切り 500 ms では負荷下で
10 発話中 4 発話が整形されずに終わることを確かめた。詳細設計書 §10。

> **750 ms でも足りない（2026-08-14 / 実機の肉声）。** 上の実測はすべて**3 秒の発話**で
> 行っており、**入力が長ければ生成も長くかかる**という依存を条件に含めていなかった。
> 実機の履歴 11 件では、**40 字以上の 8 件がすべて打ち切られて生テキストへ縮退した**
> （効いたのは 18 字以下の 3 件だけ。実測の 1 件は `refine 791 ms`）。
> **FR-5 は実運用の発話長では機能していない。**
>
> **打ち切りを延ばすだけでは解けない。** NFR-P6（1 秒）の予算が先に尽きる
> （実測 1142 ms で既に超過）。要件そのものの変更になるので、フェーズ 2 で決める。
> 要件定義書 §2.8.4。

## 8. UI 設計

### 8.1 HUD の配置

- 表示先は**常に内蔵ディスプレイ**（FR-3）。外部ディスプレイで作業中も内蔵側に表示する。
- 内蔵ディスプレイは `NSScreen.screens` から `safeAreaInsets.top > 0`（notch の存在）で判定し、該当がなければ `NSScreen.screens.first` にフォールバックする。
- ウィンドウレベルは全画面表示アプリより上に出す必要がある。`NSPanel` を `.nonactivatingPanel` で構成し、フォーカスを奪わない。

> **フォーカスを奪わないことは必須要件である。** 挿入先アプリのフォーカスが外れると、テキストの挿入先が失われる。

### 8.2 表示内容

| 状態 | 表示 |
|---|---|
| `idle` | 非表示 |
| `recording` | 録音インジケータ（音量連動）＋ 現在の言語（日/EN）＋ 暫定テキスト（末尾 2 行程度） |
| `finalizing` / `refining` | 処理中インジケータ |
| `inserting` → 完了 | チェックマークを短時間表示して収納 |
| エラー | エラー内容を数秒表示 |

### 8.3 notch UI の実装方式

| 案 | 内容 | 判断 |
|---|---|---|
| A | [DynamicNotchKit](https://github.com/MrKai77/DynamicNotchKit)（MIT / macOS 13+ / 活発）を採用 | **採用**。notch の形状検出と展開アニメーションは自前実装するとコストが高い |
| B | `NSPanel` を自前実装 | 不採用。ただし DynamicNotchKit が FR-3（表示先の固定）に対応できない場合は自前実装へ切り替える |

**確認事項**: DynamicNotchKit が「外部ディスプレイ使用中に内蔵ディスプレイへ表示する」制御に対応しているかは未確認。詳細設計時に検証し、非対応なら案 B へ切り替える（V-5 として §11 に追加）。

## 9. データ設計

すべて `~/Library/Application Support/GhostVoice/` 配下に置く。音声データは一切保存しない（FR-12 / NFR-V2）。

### 9.1 設定 (`settings.json`)

| キー | 型 | 既定値 | 説明 |
|---|---|---|---|
| `hotkey` | オブジェクト | 右 Option | PTT キー |
| `undoHotkey` | オブジェクト | ⌃⌘Z | Undo キー。PTT キーと修飾キーが衝突しないこと |
| `locale` | 文字列 | `ja-JP` | 認識ロケール |
| `transcriberKind` | 列挙 | `dictation` | `dictation` / `speech`（NFR-M1） |
| `refinementEnabled` | 真偽 | `true` | LLM 整形の有効化 |
| `refinementTimeoutMs` | 整数 | `750` | 整形の打ち切り時間（NFR-P4 の目標値 500 ms とは別。§7） |
| `historyLimit` | 整数 | `50` | 履歴保持件数 |

### 9.2 ユーザー辞書 (`vocabulary.json`)

固有名詞の配列。各項目は「正しい表記」と、任意で「誤認識されやすい表記」の配列を持つ。整形プロンプトへ注入する（FR-6）。

### 9.3 履歴 (`history.json`)

| フィールド | 説明 |
|---|---|
| `id` | 識別子 |
| `timestamp` | 発話日時 |
| `rawText` | 生テキスト（Undo 用、FR-7） |
| `refinedText` | 整形後テキスト |
| `locale` | 使用ロケール |
| `insertionMethod` | `ax` / `pasteboard` / `clipboardOnly` / **`notInserted`**（V-3 の実地データとして活用）。**例外が 2 つある**: **secure input による拒否はここに現れない**（履歴そのものを作らないため。詳細設計書 §6.4）。**中断された発話は `notInserted` で現れる**（挿入経路を 1 つも通っていないので、経路の集計からは除くこと。§4） |

`historyLimit` を超えた分は古いものから削除する。

## 10. 権限とビルド構成

| 項目 | 内容 |
|---|---|
| App Sandbox | **無効**（AX API に必須） |
| Hardened Runtime | 有効 |
| 必要な Info.plist | `NSMicrophoneUsageDescription`（**`NSSpeechRecognitionUsageDescription` は不要**。`SpeechAnalyzer` は音声認識の TCC を要求しない。実測 V-14） |
| 必要な TCC 権限 | マイク、アクセシビリティ（`kTCCServiceAccessibility` と `kTCCServicePostEvent` の両方）、キーイベント監視（`kTCCServiceListenEvent` / 入力監視。ホットキーの `CGEventTap` に要る）。**音声認識は不要**（実測 V-14） |
| `LSUIElement` | `true`（Dock に表示しない） |
| 配布 | Developer ID 署名 + notarization。Mac App Store は不可（要件定義書 §5） |

> `AXUIElement` 系 API は `kTCCServiceAccessibility`、`CGEvent.post` は `kTCCServicePostEvent`、`CGEvent.tapCreate`（ホットキー）は `kTCCServiceListenEvent` という**それぞれ別の TCC サービス**を使う。前 2 つは「システム設定 > プライバシーとセキュリティ > アクセシビリティ」に、`kTCCServiceListenEvent` は「入力監視」に表示されるが、内部的にはいずれも別枠である。二段構えの挿入（§5.2）は前 2 つを、ホットキー監視は 3 つ目を必要とする。
>
> **どれか 1 つを他の判定に流用してはならない。** 片方だけ許可された状態は原理的にありうるため、値が一致する機体では取り違えに気付けない（詳細設計書 §2.2 / §6.2）。

## 12. テスト方針

| 層 | 対象 | 方法 |
|---|---|---|
| 単体 | `Refiner`, `Vocabulary`, `HistoryStore`, `SettingsStore` | GhostVoiceCore の XCTest。外部依存はモック |
| 単体 | `TranscriptionEngine` | 音声ファイルを入力とするゴールデンテスト。既知の音声に対する認識結果を回帰確認する |
| 結合 | 挿入経路 | 主要アプリ（Slack / Chrome / Xcode / Notion / ターミナル）での手動確認（V-3） |
| 性能 | NFR-P1〜P6 | 各段に計測点を置き、履歴とともにログ出力する |

**ゴールデンテスト用の音声資産は `say` コマンドで再生成可能にする。** 本設計の調査で用いた 103 秒の日本語音声がそのまま使える。
