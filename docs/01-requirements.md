# Ghost Voice 要件定義書

- 文書番号: GV-REQ-001
- 版: 1.0
- 作成日: 2026-08-13
- 対象: macOS 向けローカル音声ディクテーションツール「Ghost Voice」

---

## 1. 背景と目的

### 1.1 背景

音声入力（ディクテーション）は、キーボード入力より高速に文章を生成できる手段である。しかし現状の選択肢には以下の課題がある。

| 選択肢 | 課題 |
|---|---|
| macOS 標準ディクテーション | 精度が低く、フィラーや言い直しがそのまま残る |
| クラウド型サービス（Aqua Voice 等） | 音声データが外部に送信される。従量課金でコストが増大する |
| Whisper 系ローカルツール | モデルを数百 MB〜数 GB 同梱する必要があり、アプリが重い |

### 1.2 目的

macOS 26 が標準搭載する `Speech` framework（`SpeechAnalyzer`）と `FoundationModels` framework のみを用い、**外部通信ゼロ・モデル同梱ゼロ**で、クラウド型サービスに匹敵する速度と品質のディクテーション体験を実現する。

### 1.3 必須条件（発注者提示）

| ID | 条件 | 判定 |
|---|---|---|
| C-1 | 早くトランスクリプトできること | 達成見込み（§2.2 実測） |
| C-2 | 容量的にも軽いこと | 達成見込み（§2.3 実測） |
| C-3 | 外部の LLM / API を使わないこと | 達成（全処理が OS 内蔵フレームワーク） |

## 2. 技術調査結果

本章の数値はすべて**開発機（MacBook Pro / Mac15,3 / Apple M3 / 16GB / macOS 26.5.2 / Xcode 26.6）での実測値**である。推測値には明示的にその旨を記す。

### 2.1 採用技術の特定

「Apple Intelligence で文字起こし」という当初の想定は、正確には以下の 2 つの独立した機能に分解される。

| 機能 | フレームワーク | Apple Intelligence の有効化 |
|---|---|---|
| 音声認識（文字起こし） | `Speech` / `SpeechAnalyzer`（macOS 26+） | **不要** |
| テキスト整形（LLM） | `FoundationModels`（macOS 26+） | **必須** |

いずれも開発機で動作を確認済み。`FoundationModels` の `SystemLanguageModel.default.availability` は `.available` を返した。

### 2.2 速度の実測

日本語 103 秒の音声ファイルをファイル一括変換した結果（各 3 回の最小〜最大）。

**所要時間はプリセットに強く依存する。** 暫定結果（volatile results）を出す `progressive*` 系は、
出さない系の 2〜4 倍かかる。HUD のライブ表示（FR-2）に暫定結果が必須のため、
**製品構成は `progressive*` 側である。**

| モジュール / プリセット | 所要時間 | 実時間倍率 | 備考 |
|---|---|---|---|
| `DictationTranscriber` / `.progressiveShortDictation` | 8.9〜15.3 秒 | 7〜11 倍速 | **製品構成（既定）** |
| `DictationTranscriber` / `.longDictation` | 3.7〜5.4 秒 | 19〜28 倍速 | 暫定結果なし |
| `SpeechTranscriber` / `.progressiveTranscription` | 1.4〜3.1 秒 | 33〜74 倍速 | 製品構成（`.speech` 選択時） |
| `SpeechTranscriber` / `.transcription` | 1.0〜1.4 秒 | 74〜103 倍速 | 暫定結果なし |

外部ベンチマークでは、同 API は Whisper Large V3 Turbo 比で 34 分動画を 45 秒 vs 101 秒、Whisper Small 比で WER 2.12% vs 3.74%（クリーン音声）と報告されている。

→ **条件 C-1 を満たす。** 製品構成の最悪値（7 倍速）でも 1 時間の音声を約 9 分で処理できる。
さらに本アプリの主用途は PTT による数秒の発話であり、**そこで効くのは一括変換の速度ではなく
確定までのレイテンシ（NFR-P3。実測 中央値 75.9〜82.5 ms / 最大 155.1 ms）である。**

> **本項の履歴**: 初版は `SpeechTranscriber` 0.76〜1.73 秒 / `DictationTranscriber` 2.72〜3.07 秒
> とだけ記していた。実装 Task 5（2026-08-14）でプリセット別に計測したところ、
> **これらは暫定結果を出さない構成の値に近く、製品構成の値ではないことが判明した**
> （`SpeechTranscriber` の値は `.transcription` の実測 1.0〜1.4 秒とほぼ重なる。
> `DictationTranscriber` の 2.72〜3.07 秒はどの構成でも再現せず、最も近い `.longDictation` でも 3.7 秒からである）。
> 製品構成の値へ差し替えた。詳細設計書 §11.2 に同じ表がある。

### 2.3 容量の実測

- **アプリ本体にモデルを同梱する必要がない。** 同種の OSS 実装 `yap` の配布サイズは約 4 MB。
- 音声認識モデルは OS が `AssetInventory` 経由で管理する（システム領域、実測 340 MB、OS 共有・自動更新）。アプリのディスク使用量には計上されない。
- 日本語モデルのインストールをアプリ側コードから実行し、成功を確認済み（`AssetInventory.status` が `.supported` → `.installed` に遷移）。

→ **条件 C-2 を満たす。**

### 2.5 精度の実測（重要）

同一の合成音声（`say -v Kyoko` / 103 秒 / 参照 529 字）を 2 モジュールで比較した結果、
**日本語の認識精度に有意な差は無かった。**

| モジュール | CER | 編集距離 | 差分箇所 |
|---|---|---|---|
| `DictationTranscriber` | **3.02 %** | 16 | 11 |
| `SpeechTranscriber` | **3.21 %** | 17 | 13 |

差は 529 字中 1 文字ぶんである。**精度でモジュールを選ぶ根拠は無い。**

> **上表は句読点と空白を除いて比較した値である。この正規化が結論を左右する。**
>
> | 正規化 | `DictationTranscriber` | `SpeechTranscriber` | 優位 |
> |---|---|---|---|
> | 句読点を除去（本書の採用値） | 3.02 % | 3.21 % | Dictation |
> | 句読点を残す | 5.85 % | 4.96 % | **Speech** |
>
> 句読点を残すと**結論が逆転する**。本書が除去側を採る理由は、本アプリの経路が
> 「認識 → LLM 整形（句読点を補う。FR-5）→ 挿入」であり、**認識器の句読点は
> 後段で書き換えられるため製品の出力品質に効かない**からである。
> 除去側の CER は「LLM が直せない誤り」を測っている。
> いずれにせよ**どちらの正規化でも差は 1 ポイント未満であり、有意ではない。**

差が出るのは精度ではなく**出力の体裁**である。

| 観点 | `DictationTranscriber` | `SpeechTranscriber` |
|---|---|---|
| 句点（。） | 16 個（原稿 17） | 16 個（原稿 17） |
| 読点（、） | **3 個（原稿 18）。ほとんど落とす** | 10 個（原稿 18） |
| 疑問符（？） | **付与する**（「ございますか？」） | 付与しない |
| 固有名詞 | 英字へ正規化（アップル→`Apple`、Mac→`Mac`） | かな維持（Mac→マック） |
| 固有の誤り | 「という」→「と言う」、「セキュリティ」→「セキュリティー」 | 「話者」→「社」、「文字起こし」→「文字を起こし」、「挙げられ」→「上げられ」 |

両モジュールに共通の誤り: 「従量課金」→「重量課金」、「高精度」→「高度」、「基本設計」→「基本設定」、
「詳細設計」→「詳細設定」、「第三」→「第 3」、「一時間」→「1 時間」、「および」→「及び」。

**誤りの過半は聞き違いではなく表記の正規化である**（漢数字→算用数字、かな→英字、かな→漢字）。
LLM 整形（FR-5）とユーザー辞書（FR-6）で吸収できる余地が大きい。

→ **既定は `.dictation` とする。根拠は固有名詞の英字化である。**

| 判断材料 | 評価 |
|---|---|
| **固有名詞の英字化** | **採用理由。** `.dictation` は「Mac」「Apple」を英字で出す（`.speech` は「マック」「アップル」）。本ツールの想定利用は Slack・エディタ・技術文書への音声入力（UC-1）であり、技術用語が正しい表記で出ることが直接の実利になる |
| 疑問符の付与 | 補助的な理由。`.dictation` のみ付与する |
| CER | **判断材料にしない。** どちらの正規化でも差は 1 ポイント未満で有意ではない |
| 一括変換の速度 | **判断材料にしない。** `.speech` が 4〜6 倍速いが、速度が効くのは録音済みファイルの一括文字起こしであり、これは §5 で明示的にスコープ外としている。PTT で効くのは 1 発話あたりの確定レイテンシ（NFR-P3。中央値 75.9〜82.5 ms）で、数秒の発話に対して両モジュールとも桁違いに速く体感差は生じない |

**ただしこれは現時点の判断であり、肉声（§7 V-1、未実施）で有意差が出れば覆る。**
LLM 整形（FR-5）の実装後に、固有名詞の英字化が整形側で吸収できると判明した場合も同様である。
差が僅少である以上、NFR-M1（差し替え可能）は「念のため」ではなく実際に必要な備えである。

> **本項の履歴**: 初版は「日本語では `DictationTranscriber` が明確に優位」とし、
> `SpeechTranscriber` の誤りとして「要件定義を完了させ」→「要件を**完了了**させ」を挙げていた。
> 実装 Task 5（2026-08-14）で CER による定量比較を行ったところ、**この誤りは再現せず
> 両モジュールとも正しく認識した**。「明確に優位」も再現しなかったため、本項を事実へ書き換えた。
> 再現した差異（「話者」→「社」、「Mac」→「マック」、「文字起こし」→「文字を起こし」）は上表に残してある。
> 誤りの全一覧は詳細設計書 §11.2。

> **未検証**: 上記は合成音声（`say -v Kyoko`）による比較である。合成音声は発話が均質すぎて
> 実利用の精度を代表しない。**実際の肉声で再検証すること（§7 V-1。未実施）。**

### 2.6 語彙ヒント（`contextualStrings`）は無効

`AnalysisContext.contextualStrings[.general]` に専門用語 9 語を投入し、投入あり／なしで同一音声を処理したところ、**両モジュールとも出力が 1 文字も変化しなかった**。

→ **API レベルの用語辞書は使えない。固有名詞の精度対策は LLM 整形側に集約する（FR-6）。**

### 2.7 LLM 整形のレイテンシ実測

```
session init      : 0.028s
prewarm()         : 0.008s
[1回目] 1.906s   ← モデル初回ロードを含む
[2回目] 0.347s
[3回目] 0.450s
ストリーミング first-token: 0.272〜0.318s / 完了: 0.354〜0.462s
```

→ **（設計調査時の結論）アプリ起動時に温めておけば、整形はおおむね 0.4 秒台。**
これが当初の既定タイムアウト 500ms の根拠だった（**現在の既定は 750 ms**。下記）。

---

**ここから下が正。** 上は設計調査時の数値と結論であり、実装後の実測（Task 6・`refine()` 全体・
10 サンプル）で下記へ更新された。

| 条件 | 中央値 | 最大 | 500ms 超 |
|---|---|---|---|
| 低負荷 | 0.389 秒 | 0.413 秒 | 0/10 |
| 機体が並行して他の処理をしている条件 | **0.461 秒** | **0.518 秒** | **1/10** |

**余裕は薄く、同時実行負荷に敏感。** 負荷下の余裕は 39 ms しかない。
500ms を超えた発話は整形されず生テキストのまま挿入される（壊れはしないが FR-5 が効かない）。

**→ 既定タイムアウトを 750 ms へ引き上げた（Task 10）。** M5（現 M5a）を端から端まで実測したところ、
負荷下では 10 発話中 4 発話が 500 ms を超えており（超過分は 501〜527 ms）、
**FR-5 が実運用で半分近く効かない**状態だった。NFR-P4 の目標値 500 ms は変えない
（目標と打ち切りは別の数である）。根拠と予算配分は詳細設計書 §10。

> **打ち切り 750 ms の効く範囲は、フェーズ 2 の裁定（§2.8.6）で狭まった。**
> 750 ms は**差し替えできない挿入先（整形を待つしかない分岐）だけ**の打ち切りになり、
> 差し替えできる挿入先では整形はクリティカルパスから外れて別の締め切り（NFR-P6b）で走る。
> **既定値そのものは 750 ms のまま変えない**——待つ分岐の予算計算（M2 199 ms + 打ち切り + M4 50 ms ≦ 1000 ms）は
> 裁定の前後で変わらないためである。**M2 の測り直し（V-12 の修正）で合計は 977 → 999 ms になり、余裕は 1 ms しか無い**（詳細設計書 §10）。

**ただし `LanguageModelSession.prewarm()` を呼ぶだけでは温まらない。** Task 6 の実測で、
`prewarm()` が 0.013 秒で返った後も 1 回目の `respond` に 3.318 秒掛かり、2 回目が 0.347 秒だった。
`prewarm()` はロードの開始を促すだけで完了を待たない。ロードを実際に強いるのは `respond` の方なので、
**起動時に捨て推論を 1 回通す**必要がある（`FoundationModelRefiner.prewarm()` はそう実装してある）。
モデルの常駐はプロセス外のデーモン側にあり、セッションやプロセスの生存期間とは独立している。

### 2.8 判明した制約

| ID | 制約 | 影響 |
|---|---|---|
| L-1 | 話者分離 API が `Speech` framework に存在しない | 今回はスコープ外（§5） |
| L-2 | Apple Silicon 必須（Intel Mac 非対応） | 対象環境を限定 |
| L-3 | 1 回の解析 = 1 ロケール | 言語は手動切替とする（FR-8） |
| L-4 | `contextualStrings` が機能しない（§2.6） | FR-6 で代替 |
| L-5 | LLM 整形が意味情報を削る場合がある | FR-7（Undo）で担保 |
| L-6 | ユーザー辞書の写像が語によって効かない | FR-6 の実効性に上限。§2.8.1 / R-8 |
| L-7 | 命令文に読める発話でモデルが整形ではなく回答を返す | FR-5 の出力を検査して縮退。§2.8.2 / R-7 |
| L-8 | **右 Option を持たない日本語配列の MacBook がある**（実測。スペース右が「かな・command・fn」の配列） | 既定の PTT キーが物理的に押せない。**caps lock を「修飾キー」設定で Option へ転用すると、右 Option（keyCode 61 / `NX_DEVICERALTKEYMASK`）として報告される**ので、既定のまま使える（§2.8.3） |

L-5 の実例:

```
入力: えー、エラーハンドリングが抜けてるので、そこを追加したいです
出力: エラーハンドリングを追加します。            ← 「抜けてる」が消失
```

**整形プロンプトの規則 4（「話者の意図・情報を変更しない。要約しない。語を削らない」）は、
これを防ぐために書かれたが防げていない。** Task 6 の実測で上記が再現した。
規則 4 は信頼できない。

**過剰要約に対する実効的な安全網は Undo（FR-7）である。** 整形結果を生テキストへ戻す
10 秒窓がこれを担保する。**ただし自動で戻せるのは差し替え可能な経路で挿入した発話に限る**
（FR-7 の細目 / §2.8.6）。それ以外の経路では生テキストをクリップボードへ取り出す操作に縮退し、
**利用者が自分で貼り直すことになる。**
長さによる自動検出は採れない。過剰要約は「短くなる」方向であり、
フィラー除去による正常な短縮（実測で 出力/入力 = 0.53 の例がある）と区別が付かないため、
下限を設けると正常な整形を誤って捨てることになる。

#### 2.8.1 L-6: ユーザー辞書の写像が語によって効かない

固有名詞の誤認識対策は LLM 整形プロンプトへの注入だけが手段（L-4）だが、
**その注入が語によって効かない。** Task 6 の実測（新規セッション・temperature 0）:

| 誤認識 → 正規表記 | 結果 |
|---|---|
| ネクサデータ → Nexadata | ○ |
| アイフォン → iPhone | ○ |
| ユーチューブ → YouTube | ○ |
| ジーエイエス → Google Apps Script | ○ |
| マイクロシーエムエス → microCMS | **×**（再現性 100 %） |
| エヌピーエム → npm | **×** |
| ジーアイティーハブ → gitHub | **×**（モデル独自の綴り「GitHub」になる） |

`microCMS` は正規表記の綴りを `microCMS` / `MicroCMS` / `Microcms` / `MICROCMS` / `microcms`
の 5 通りに変えても 1 度も置換されなかった（正規表記をカタカナ「マイクロCMS」にした場合のみ成功）。
頭字語をカタカナで読み上げた誤認識（シーエムエス = C-M-S、エヌピーエム = N-P-M）が
効きにくい傾向はあるが、`ジーエイエス → Google Apps Script` は効くため法則は確定していない。

改善を 2 通り試したが、いずれも**現状より悪化**したため採用しなかった:

1. **写像を `instructions`（セッション生成時）側へ入れる** → 効かないままで、
   さらに成功していた `ネクサデータ → Nexadata` まで失敗するようになった
2. **命令を強める**（「**必ず**置換」「矢印の左の表記を出力に残してはいけない」）→
   効かないままで、**フィラー除去（規則 1）が壊れた**（出力に「えー、」が残る）。
   辞書の指示を強めると整形の主目的と競合する

→ **FR-6 は「効く語と効かない語がある」前提で運用する。** 効かない語は生の誤認識のまま
挿入され、ユーザーが手で直すことになる。根本的な改善には認識側での対策
（`SFCustomLanguageModelData` によるカスタム言語モデル。詳細設計書 V-8）の検討が要る。

#### 2.8.2 L-7: 命令文に読める発話でモデルが回答を返す

発話が命令文・依頼文に読めると、モデルは整形ではなく**その依頼への回答**を生成する。
Task 6 の実測（新規セッション・temperature 0・再現性 100 %）:

```
入力: えー、この関数にエラー処理を追加したいです
出力: 関数にエラー処理を追加するには、try-exceptブロックを使用します。…（全 484 字、Python のコード片を含む）
```

エンジニアの技術的口述はこのツールの主要用途なので、実用上の影響が大きい。
原因は「1 ターンのユーザーメッセージとして命令文を渡せば、`instructions` よりその場の指示が
勝つことがある」という LLM 一般の性質にあり、**完全には消せない。** 2 段で受け止める:

1. **発話を必ず `整形対象:` の枠で包む**（`RefinementPrompt.prompt`）。
   実測で逸脱は 5 発話中 4 → 1 に下がった
2. **残りは出力を検査して落とす**（`RefinementGuard`）。整形は入力より大きく伸びないという
   性質（実測で 出力/入力 は最大 1.00、逸脱は最小 2.6 倍）、コードフェンスの有無、そして
   **入力に無い文字を 1 字も足していないこと**（§2.8.8）で判定し、
   通らない出力は捨てて生テキストへ縮退する

→ 逸脱した発話は**整形されない**（生テキストのまま挿入される）が、
モデルの回答がユーザーのテキスト欄に入ることは無い。

#### 2.8.3 L-8: 右 Option を持たない配列がある（実測 / 権限付与セッション）

**日本語配列の MacBook 本体キーボードで、スペース右が「かな・command・fn」の配列が存在する。**
右 Option が物理的に無いので、**既定の PTT キーを押せない。**

要件定義の時点では R-1（右 Option を押しながら文字を打つと `å` が入る）を既知の副作用として
挙げていたが、**「そもそも右 Option が無い機体がある」は想定していなかった。**
実機に触れて初めて出た欠落である。

実測（使い捨てのイベントタップで `flagsChanged` のデバイス依存ビットを観測）:

| 押したキー | keyCode | 論理マスク | デバイス依存ビット |
|---|---|---|---|
| caps lock（既定のまま） | 57 | `capslock` | **無し** |
| `fn` | 63 | `fn` | **無し** |
| 左 option | 58 | `option` | 左 option (0x20) |
| 右 command | 54 | `command` | 右 command (0x10) |
| 右 shift | 60 | `shift` | 右 shift (0x04) |
| **caps lock（システム設定 > キーボード > 修飾キー で Option へ転用）** | **61** | `option` | **右 option (0x40)** |

**転用した caps lock は右 Option として報告される。** したがって既定のバインドのまま使え、
設定もコードも変更が要らない。

**これは代替手段であると同時に、右 Option より望ましい。** caps lock は日本語配列で
ほぼ使わないキーなので、R-1 の副作用（PTT キーを押しながらの打鍵）が実質的に起こらず、
本物の左右 Option を使うショートカットとも衝突しない。

**caps lock と `fn` はデバイス依存ビットを報告しないため、転用しない限り PTT に使えない**
（詳細設計書 §2.3 の左右判定が成立しない）。

#### 2.8.4 実機の肉声で判明した 2 件（2026-08-14 / 権限付与セッション）

**フェーズ 1 の CLI を実機で初めて通したときに、合成音声では出なかった欠陥が 2 件出た。**
どちらも「短い合成発話で決めた値・確かめた性質が、実用の発話長で成立しない」形である。

##### (1) V-12 が再現した——末尾が失われる

121 字・区切りの多い肉声の発話で、**末尾 約 38 字が挿入されなかった。**

| | 内容 |
|---|---|
| 挿入された末尾 | …このままちょっとキャップスロックを**話して** |
| 暫定表示（`[録音中]`）の末尾 | …このままちょっとキャップスロックを**ロを押したまま喋ってるんですが、これを押したままコントロールシーよりも押してみます。** |

原因（**当時の実装**）: `completeUtterance` は**解放後の最初の確定**で待ちを解き、そこで
`latestFinal` を `await` を挟まず同期的に読んでいた。**その後に届いた確定は積まれても
二度と読まれなかった**（§10 の M2）。

合成音声 103 秒では「解放後に 2 件目」が起きなかっただけで、**肉声・長い発話・区切りの多い
話し方では 1 回目で起きた。** 「再現しなかった」を「起こらない」と読んではならない実例である。

**これは発話を失う欠陥である。** **フェーズ 2 で塞いだ**（2026-08-14）。
確定待ちを「解放後の最初の確定」から「**結果ストリームの終端**」——これ以上テキストが
来ないと判る時点——へ移した（詳細設計書 §10 の「M2 の定義を…」／ §13 の V-12）。
代償は M2 が 約 11 ms 伸びたこと。**回帰を止めているのは代役による単体検査である**
（`doesNotDropSecondFinalAfterRelease`）——**実音声ではこの条件を一度も起こせていない。**
**実機の肉声での確認は V-31 として登録した。**

##### (2) LLM 整形が、実用の発話長で 1 件も効いていない

実機の履歴 11 件の内訳:

| 発話の長さ | 件数 | 整形された件数 |
|---|---|---|
| 40〜121 字 | 8 | **0** |
| 18 字 | 1 | 1 |
| 5 字 | 2 | 2 |

**整形が効いたのは 18 字以下の 3 件だけで、40 字以上は 8 件すべて打ち切られて
生テキストへ縮退した**（`refinedText` が無い）。実測の 1 件は `refine 791 ms`。

原因は**打ち切り 750 ms を決めた実測の条件**にある。Task 10 の M3（中央値 355〜364 ms）は
**3 秒の合成発話**で測った値で、**入力が長ければ生成も長くかかる**という当然の依存を
条件に含めていなかった。**FR-5 は実運用の発話長では機能していない。**

**打ち切り時間を延ばすだけでは解けない。** NFR-P6（当時の定義。キー解放 → 挿入完了 1 秒。現在は NFR-P6a / NFR-P6b へ分けた）の予算が
先に尽きる（実測 1142 ms で既に超過）。

**→ 裁定は §2.8.6 にある。当時の選択肢として挙げた「長い発話では整形を待つ」も
「NFR-P6 を発話長の関数にする」も採らなかった。** 生テキストを先に挿入し、整形は後から条件付きで差し替える形に要件を
書き換えた（FR-5 / FR-7 / NFR-P6a / NFR-P6b / NFR-V3）。

#### 2.8.5 V-3 の実施で判明した 3 件（2026-08-14 / 実機）

`SystemAccessibility.focusedElement()` が `AXUIElementCreateSystemWide()` から

5 秒へ伸ばしても **0 ms で落ちる**ので、相手の応答待ちではない。

| メモ | `AXTextArea` | ✓ |
| Chrome アドレスバー | `AXTextField` / `AXComboBox` | ✓ |
| Chrome ページ内 | `AXWebArea` | ✗ |
| ターミナル / cmux | `AXTextArea` | ✗ |

修正後、**メモと Chrome のアドレスバーで `insertionMethod = ax` になった。**

| | `insert` | `total` |

**最前面の pid は `CGWindowListCopyWindowInfo` から取る。**
`NSWorkspace.frontmostApplication` は通知で更新されるため、**ランループを回さない文脈
（挿入器は actor 上で動く）では古い値を返し続ける**（実測: 12 回中 10 回、追随しなかった）。

##### (2) LLM がユーザーの質問に答え、その答えが発話として挿入された

**このプロジェクトで最も重い欠陥である。テキストを失うより重い——言っていないことを
言ったことにしている。** しかも内容は作り話である（モデルは天気を知らない）。

```
raw    : 東京の天気どんな感じですか？   → refined: 東京の天気は晴れています。
raw    : 明日の天気って何でしょうか？   → refined: 明日の天気は晴れそうです。
```

L-7 / R-7 として挙げ、`RefinementGuard` で受け止めるとしていた経路だが、**防御が効かなかった。**
既存の検査は**長さ**（出力が入力の 1.5 倍を超えないか）と**コードフェンスの有無**しか
見ておらず、**出力が入力の変換になっているかを一度も確かめていなかった。**
今回の逸脱は入力より短い（比 0.93）ため素通りした。

防御を 1 つ足した（`RefinementGuard`）。**ただし、このとき足した指標は誤っていた。
翌日の実測で作り直している——§2.8.7。**

##### (3) Pasteboard の復元待ち 120 ms が不足（既定を 300 ms へ）

Electron 製の端末アプリ（cmux）へ挿入すると、**相手が ⌘V を処理する前に復元が走り、
戻された「前のクリップボードの内容」が貼られた。** 履歴には正しい発話が `pasteboard` で
成功として記録されるので、**「成功と記録されるのに、そこに違うテキストがある」**形である。
連続発話で悪化した。`--paste-restore-delay-ms 300` で解消。

Task 8 の実測（35 ms）が**下限であって上限ではない**と自ら明記していたとおりの結末である
（計測は自プロセスの軽い `NSTextView` に対して行われ、WindowServer を経由していなかった）。

#### 2.8.6 フェーズ 2 の裁定: 生テキストを先に挿入し、整形は後から差し替える（2026-08-14 / 発注者承認）

**本項は実測ではなく裁定である。** 根拠になった実測は §2.8.4 (2) と §2.8.5 (1)。
設計の全文は独立に作成された 2 本
（`.superpowers/sdd/2026-08-14-ghost-voice-phase2/design-refinement-budget-opus.md` と
同 `-codex.md`）で、**両者は独立に同じ結論に達した。**

##### 何が両立していなかったか

**FR-5（整形）・FR-7（Undo）・NFR-P6（当時の定義。1 秒）の 3 つの必須要件が、同じ 1 秒の予算を奪い合っていた。**

| # | 事実 | 出所 |
|---|---|---|
| 1 | 整形の所要は**入力が長いほど伸びる**。実機の履歴 11 件で、**40 字以上の発話 8 件がすべて打ち切り（750 ms）に掛かって生テキストへ縮退した。** 整形が効いたのは 18 字以下の 3 件だけ | §2.8.4 (2) |
| 2 | **打ち切りを延ばすだけでは解けない。** 実測で既に `total 1142 ms` と NFR-P6（当時の定義。1 秒）を超えている | §2.8.4 (2) / §2.8.5 (1) |
| 3 | Undo（FR-7）は `refinedText != nil` の発話しか戻せないので、**実運用ではほぼ発動しない**（1 の帰結） | 上記 |

##### 裁定（6 点）

1. **生テキストを先に挿入し、整形は後から条件付きで差し替える。** 差し替えが安全に成立する条件が揃わない挿入先では**何も書き換えない。** 縮退先は常に「生テキストが欄にある」＝**現行の正常系そのもの**であり、この設計には「現状より悪くなる領域」が無い。
2. **NFR-P6 の 1 秒が守るのは「整形済みテキスト」ではなく「まず使えるテキスト」になる。** 要件を **NFR-P6a**（発話終了 → テキストが出るまで）と **NFR-P6b**（発話終了 → 整形が反映されるまで）へ分ける（§4.2）。
3. **FR-7（Undo）と「整形の差し替え」は同一の原始操作である。** 向き（生 → 整形／整形 → 生）が違うだけで、条件も手順も後始末も同じものを使う。**別々の機能として実装してはならない**（二重投資になり、片方だけ直る事故を生む）。
4. **⌫ の送出と ⌘Z の送出は採らない。** どちらも「届いたか判らない操作で、先に消す」形になり、**消えたが書けていない窓で発話を失う。** `CGEvent.post` は `Void` を返し、届いたかを知る術が無い（詳細設計書 §6.3）。⌘Z はさらにアンドゥ単位が判らず、利用者自身の編集を巻き込む。
5. **NFR-V3 に最小の例外を認める**（§4.2 のプライバシー表）。**この例外は発注者が明示的に承認した。** 認めなければ「自分が書いた文字列がまだそこにあるか」を確かめられず、位置の算術だけを頼りに他アプリのテキストを書き換えることになるので、**差し替えも自動 Undo も安全には実装できない。**
6. **Pasteboard 経路で挿入した発話は差し替えられない。** 送出が届いたかを判定できず、範囲も持てないためである。**FR-7 はこの経路では「戻せる」を満たせない。**

##### 差し替えが成立する条件（すべて満たしたときだけ書き換える）

| # | 条件 | 何を防ぐか | 確度 |
|---|---|---|---|
| C-1 | その発話が **`.ax` 経路で挿入された** | Pasteboard / `clipboardOnly` には範囲が無い | 確実（挿入結果から判る） |
| C-2 | **挿入時に握った要素参照が生きている**（プロセス内メモリのみ。ディスクへ持ち越さない） | 別プロセス・別セッションからの書き換え | 設計上の性質 |
| C-3 | **現在の最前面 pid が挿入時の pid と一致する** | 別アプリへ移ってから撃つ | 既存 API で判る |
| C-4 | **現在のフォーカス要素が挿入時の要素と一致する** | 同じアプリの別の入力欄 | **未実測**（要素同一性が時間を跨いで期待どおりか） |
| C-5 | **`kAXSelectedTextRange` と `kAXSelectedText` が両方 settable** | 範囲を選べない相手に書きにいく | **未実測**（V-23） |
| C-6 | **記録した範囲を読み戻した文字列が、自分が書いた文字列と一致する** | 利用者の編集・カーソル移動・範囲の単位ずれ・アプリによるテキスト変換 | **未実測**（V-24） |
| C-7 | **そのプロセスで、本セッション中に「喪失の疑い」（事後検査が元の文字列でも新しい文字列でもない第三の値）を出していない** | 一度でも喪失を疑わせた相手には以後試さない。**無言失敗（事後検査が「元の文字列のまま」。R-4）では締め出さない**——何も書き換わっていないので危険ではないため（詳細設計書 §8.3 が正。当初ここは「事後検査を落としていない」と書いており、無言失敗も含む読みになっていた。2026-08-15 訂正） | 設計上の性質 |

**C-6 が要である。** 位置の算術（「n 文字ぶん戻る」）を信じず、**読み戻して一致したときだけ書く。**
一致しなければ理由を問わず中止する。**文字数の数え方は 3 通りに割れる**ため
（`👨‍👩‍👧‍👦` は `count 1` / `utf16 11` / `unicodeScalars 7`。上記設計書の実測）、
算術だけを頼りにすると「判らないまま書く」経路が残る。C-6 はそれを「間違えたら中止する」に変える。

##### この裁定が抱える未実測

**V-23〜V-30**（詳細設計書 §13）。とくに次の 2 つが重い。

- **V-23（主要アプリで `kAXSelectedTextRange` が settable か）** は裁定の前提そのものである。全滅なら差し替えは一度も成立しない。**ただしその場合の挙動は現状と同じ**になる（全発話が「待つ」分岐へ落ちる）ので、失うのは実装の工数だけである。
- **V-26（差し替えの事後検査で「消えただけ」が起きるか）** は、この設計で唯一「発話が欄から消えうる」経路である（§6 の R-9）。**発生は未観測、原理的には否定できない。**

#### 2.8.7 整形の検査が「言っていないこと」を通していた（2026-08-15 / 実機）

**§2.8.5 (2) で足した指標は誤っていた。** 翌日、V-37（「長い発話で正当な整形を捨てていないか」）を
実測したところ、**疑いは外れており、代わりに逆向きの穴が見つかった。**

##### 疑いは外れていた——発話長は原因ではない

旧指標（共通部分列 ÷ 短い方の長さ）は、長い発話ほど**上がる**（19 字 0.933 → 124 字 0.991）。
**5〜124 字の 9 例すべてで正当な整形は受け入れられていた。**
A4 が「56 字で 10/10 捨てられた」と報告した計測は、**フィクスチャ音声を 10 秒で切っており、
認識結果が文の途中で終わっていた**。同じ長さ帯の**言い終えた**発話は、
認識から差し替えまで通して **3/3 で整形が反映される**（詳細設計書 §5.5.1 の対照実験）。

##### 実際の穴——指標は「足された語」に対して盲目だった

`共通部分列 ÷ min(入力, 出力)` は `max(残存率, 由来率)` に等しく、**2 方向の甘い方**を採る。
**入力が丸ごと残っていれば、追加が何字あっても 1.000 になる。**

```
raw    : 本日は…まず前回のミーティングの振替                    （36 字）
refined: 本日は…まず前回のミーティングの振替についてお話しします。（47 字）
```

**「についてお話しします」は誰も言っていない。** 旧指標は 1.000 を返し、長さの検査も通り、
**利用者の欄へ入っていた。** これは §2.8.5 (2) と同じ欠陥——
**言っていないことが利用者の発話として挿入される**——であり、
**足した防御が、防ぐはずのものの別の形を通していた。**

##### 直した形

指標を「**入力にも句読点にも由来しない文字が何字足されたか**」に置き換えた（境界 3 字）。
**観測した範囲では**正当な整形の最大は 2 字、逸脱の最小は 5 字。**句読点を勘定に入れないので、
句読点の数に比例して増える成分は無くなった**（V-37 の再発防止）。**ただし「発話長に依存しない」
とは言えない**——長い発話ほど数字や表記正規化の機会が増えれば追加字数も増えうる（未実測）。
**辞書を先に入力へ当ててから測る工夫（`applyingVocabulary`）は残してある。**
詳細と実測表は詳細設計書 §5.5.1。

> **この「境界 3 字」も、その後の実測で破れた。** 標本を 13 入力から 71 入力へ広げると、
> **正当な数量正規化が境界ちょうどの 3 字に達していた**（余裕 0）。→ **§2.8.8 が現行の形である。**

##### 残る限界

**文の途中で PTT を離すと、モデルは続きを捏造する。** PTT は離した瞬間に確定するので、
**言い終える前に離せば必ずこの形になる。** 検査が捨てるので**生テキストは欄に残る**が、
**その発話では整形が効かない。** プロンプト側の対策（「続きを補わない」という規則の追加）は
**実測で出力を 1 文字も変えなかった**——規則 4（要約しない）が効かないのと同じ性質である。
**この形が実運用でどれくらいの頻度で起きるかは未実測である。**

**境界 3 字は、観測した集合を分ける 1 点にすぎない。** 実測で分けられなかった側が両方向にある——
**桁の大きい数量正規化（`千円` → `1,000円。` は追加 4）は落ち、短い意味の反転
（`成功` → `失敗。` は追加 2）は通る。** どちらも Guard の実装ロジック上そうなることは確定しているが、
**モデルが実際にその出力を返す頻度は未実測**である。**過剰要約も依然として捕まえられない。**
**これらに対する安全網は Undo（FR-7）であり、Guard ではない。** 詳細は詳細設計書 §5.5.1。

#### 2.8.8 閾値では解けなかった。曖昧な類をプロンプトで消した（2026-08-15 / V-38）

**2 回続けて「指標をいじる」で失敗している。** §2.8.5 (2) の残存率は追加に盲目だった。
§2.8.7 の「境界 3 字」も、最終レビューの反証（`review-6-refute.md` §5）が
**両方向に破れることを示した**——短い意味反転は追加 1〜2 字で通り、
`千` → `1,000` のような正当な正規化は追加 4 字で落ちる。

##### まず実測した——反証の 4 例をモデルは返さない

反証は手で構成した出力に基づいていた。**実際にモデルへ通した結果**
（2026-08-15 / MacBook Pro M3 / macOS 26.5.2 / temperature 0 / 各 3 回）:

| 入力 | 反証が想定した出力 | **実際にモデルが返したもの** |
|---|---|---|
| `成功` | `失敗。` | **応答なし**（52.1 秒暴走し `exceededContextWindowSize`） |
| `可` | `不可。` | `可`（3/3。反転しない） |
| `参加者は百人です` | `参加者は100人です。` | **応答なし**（`guardrailViolation`） |
| `千円です` | `1,000円です。` | `千円です。`（3/3。正規化しない） |

**短い意味反転は実機で一度も観測されていない。** `可` `不可` `承認` `却下` `中止` `続行` を含む
18 の短い発話すべてで、モデルは反転しなかった。**実機で観測された逸脱は
「まとまった量が足される」形だけである**（追加 6〜166 字）。

##### ただし曖昧な類は実在した——閾値をちょうど使い切っていた

反証の指摘そのものは、**別の例で裏付けられた**。数量表記の正規化は実際に起き、
**`…前年比で百二十パーセント` → `…前年比で120％` は追加 3 字＝当時の境界ちょうど**だった。
`千二百` → `1,200` なら 4 字で落ちる。**余裕は 0 で、間隙は標本の中にしか無かった。**

**問題の形はこうである。** 数量正規化は**それ自体は逸脱ではない**から許容するしかなく、
**許容した量はそのまま逸脱にも開く。** 閾値をどこへ動かしても、この二律背反は動かない。

##### 直した形——起こさせない。そして許容量を 0 にする

整形プロンプトへ**規則 5「数字の表記を変えない。漢数字は漢数字のまま、
算用数字は算用数字のまま出力する」**を足した。実測で**効いた**（数字を含む 12 発話すべてで
追加 0 字。3 回とも同一。数字を含まない発話の出力は変わらず）。

**規則 4（要約するな）と規則 6（続きを補うな）が効かなかったのに、規則 5 が効いた理由も
実測から言える**——前者はモデルに**意味の判断**を求め、後者は**表層の写像**しか求めない。
**新しい規則を足すときはこの差を先に見ること。**

曖昧な類が消えたので、検査は閾値ではなく**性質**になった:

> **整形結果は、句読点・空白・大文字小文字を除けば、入力の部分列でなければならない。**

**製品のプロンプトそのもので 71 発話（日英・1〜76 字）を実測**したところ、
**受理された 61 発話は 61/61 が追加 0 字、逸脱 9 例の最小は 6 字で、1〜5 字は 1 例も無い。**
**0 は標本から引いた線ではない。「整形は足す操作ではない」という定義である。**

大文字小文字を畳むのは英語のため（`so the meeting…` → `The meeting…` の大文字化だけで
追加 1 字が付き、許容量 0 では英語の整形が丸ごと落ちる）。畳めば英語も追加 0 字になる。

##### 捕まえられないもの（**これは直っていない。安全網で受ける**）

**この検査は「足された文字」しか見ない。削ることで意味が変わる逸脱は原理的に通る。**

| 形 | 例 | 判定 |
|---|---|---|
| **削るだけの要約** | `…が抜けてるのでそこを追加したいです` → `…を追加したいです。` | **通る** |
| **否定の脱落** | `行きたくないです` → `行きたいです` | **通る** |
| 語尾まで書き換えた要約（L-5 の実測例） | `…追加したいです` → `…追加します。` | 落ちる（追加 1） |
| 語の入れ替え | `成功` → `失敗。` | 落ちる（追加 2） |
| 語順の入れ替え | `A は B より大きい` → `B は A より大きい` | 落ちる（追加 1 以上） |

**境目は「意味が変わったか」ではなく「入力に無い文字を使ったか」である。**
文字の編集距離を測る指標は意味を見ていないので、**指標の改良では解けない。**
L-5（過剰要約）が落ちるのも、意味を見たからではなく、たまたま語尾を書き換えていたからにすぎない。

**安全網は 2 つ。どちらも実装済みである。**

- **FR-7（Undo）**——直前の挿入を戻せる（差し替えできる経路で挿入した発話に限る）。
- **履歴が `rawText` を保持していること**（`HistoryEntry.rawText`）——
  整形後だけでなく**生テキストが必ず残る**ので、利用者は言ったことを確認・回収できる。

**「守っているつもり」で書いて次の人を誤らせるより、限界を書くほうが価値がある。**
この限界を狭めたいなら、必要なのは閾値でもプロンプトでもなく、
**意味を見る手段**（生テキストと整形後を意味の水準で突き合わせる）である。**現状その手段は無い。**

#### FR-5 の細目（整形の反映）

裁定は §2.8.6。**整形の完了を待つのは、待つしかない経路だけである。**

| 分岐 | 条件 | 挿入するもの | 整形の扱い |
|---|---|---|---|
| **(a) 差し替え可能** | 挿入時点で §2.8.6 の C-1〜C-7 が見込める | **生テキストを直ちに挿入する** | 挿入と**並行**して走らせ、返り次第**同じ範囲を差し替える** |
| **(b) 差し替え不可** | それ以外（Pasteboard 経路・`clipboardOnly`・範囲を持てない相手） | 整形結果（間に合えば）／生テキスト | 従来どおり**待つ**。打ち切りは NFR-P6a の残予算（既定 750 ms） |

- **差し替えの成否によらず、生テキストは欄に残る。** 差し替えが成立しないと判ればそもそも書き換えないためである。
- 整形結果は (a)(b) いずれでも履歴に記録し、FR-9（再挿入）と FR-7（Undo）から辿れるようにする。
- **「実運用の発話長で整形が反映されること」を必須とするのは (a) の経路に限る。** (b) の経路では短い発話にしか効かないことを、要件として認める（§2.8.4 (2) の実測がそうなっている）。
- **文の途中で PTT を離した発話では、整形が反映されないことを認める。** モデルが続きを捏造し、出力の検査が捨てるためである（§2.8.7）。**縮退先は生テキストであり、発話は失われない。** 言い終えた発話では 5〜124 字のどの長さでも反映される（実測 2026-08-15）。
- **(a) の差し替えは、FR-7（Undo）と同一の原始操作で行う**（§2.8.6 の裁定 3）。

#### FR-7 の細目（Undo）

**Undo と FR-5(a) の差し替えは同じ操作であり、向き（生 → 整形／整形 → 生）だけが違う。**
条件（§2.8.6 の C-1〜C-7）・手順・失敗時の後始末は共通のものを使う。

| 押された時点の状態 | 何が起きるか | 危険度 |
|---|---|---|
| 差し替えが**保留中**（整形を待っている） | **差し替えを取りやめるだけ。何も書き換えない** | ゼロ（書き込みが 1 回も起きない） |
| 差し替えが**適用済み**（10 秒窓内） | 同じ範囲を生テキストへ差し替える | 差し替えと同じ |
| **差し替え不可の経路**で整形結果が入っている | **戻せない。** 生テキストをクリップボードへ取り出し、**「自動で戻せなかった」ことを利用者へ告げる** | クリップボードのみ |
| どれでもない | 何もしない。「戻せません」と表示する | ゼロ |

- **Pasteboard 経路で挿入した発話は「戻せる」を満たせない**（§2.8.6 の裁定 6）。要件としてそう認める。
- **⌫ の送出と ⌘Z の送出は使わない**（§2.8.6 の裁定 4）。
- **Undo の門は「メモリ上に生きている差し替えハンドル」であり、履歴ファイルではない。** ハンドルは (a) の経路でしか作られないので、`clipboardOnly` / `notInserted` の発話を戻そうとする経路が構造的に消える。

##### NFR-V3 の唯一の例外（2026-08-14 / 発注者が明示的に承認）

> **差し替え（FR-5(a) / FR-7）の検査に限り、自分が直前に書き込んだ範囲の文字列だけを読んでよい。**

**なぜ要るか。** 「自分が書いた文字列がまだそこにあるか」を確かめずに書き換えるのは、
**利用者が手で編集した内容の上に書く**ことを許すのと同じで、誤ったテキストを入れる欠陥を新設する。
例外を認めないなら差し替えは行うべきではなく、その場合 FR-5 は §2.8.4 (2) の状態のまま
（実用の発話長で整形が効かない）になる（§2.8.6）。

**例外の輪郭は次の 4 条件である。この 4 つが要件であり、緩めてはならない。**

| # | 条件 |
|---|---|
| 1 | **範囲は自分が書いた場所に限る。前後 1 文字も広げない。** |
| 2 | **用途は比較のみ。** 自分が書いた文字列と等しいかを見て、**真偽値 1 つに落とす。** |
| 3 | **保持しない。** 履歴・計測・整形・ログのどこへも渡さない。変数の寿命は比較まで。 |
| 4 | **不一致だった文字列は内容を一切見ない。**「違った」以上のことを判定に使わない。 |

**この 4 条件は単体検査で固定する**（詳細設計書 §8.3）。

**読んでよいものと読まないものを、属性の粒度で確定させる。**

| 属性 | 扱い |
|---|---|
| `AXStringForRange`（**自分が書いた範囲のみ**） | **上記 4 条件の下でのみ読む。これが例外の全部である** |
| `kAXSelectedTextRange` | 読み・書きともに行う。**返るのは位置と長さの整数 2 つで文字を含まないため、例外に当たらない** |
| `kAXSelectedText` | **書き込みのみ。読まない**（読むと利用者が選んでいる文字そのものを読むことになる） |
| `kAXValue`（欄の全文） | **読まない** |
| `kAXNumberOfCharacters`（欄の全長） | **読まない** |
| `kAXVisibleCharacterRange`（画面に見えている範囲） | **読まない** |

**この例外は §5 の「画面内容の読み取りによる文脈補正」を一切開かない。** 読んだ値は整形にも認識にも渡らない（条件 3）。

## 8. 用語

| 用語 | 意味 |
|---|---|
| PTT | Push-to-Talk。キーを押している間だけ録音する方式 |
| notch | MacBook 内蔵ディスプレイ上部の切り欠き |
| volatile result | 認識途中の暫定結果。後続の入力で書き換わる |
| finalize | 暫定結果を確定させる処理 |
| 生テキスト | LLM 整形を通す前の、音声認識そのままの出力 |
| AX API | Accessibility API（`AXUIElement`）。他アプリの UI 要素を操作する仕組み |
| 差し替え | **自分が挿入した範囲を選び直して上書きする 1 つの原始操作。** FR-5(a)（生 → 整形）と FR-7（整形 → 生）は、この操作の向きが違うだけである（§2.8.6） |
| 差し替えハンドル | 差し替えのために挿入時に握る、pid・要素参照・範囲・書き込んだ文字列の組。**プロセス内メモリにのみ持ち、ディスクへ持ち越さない** |
