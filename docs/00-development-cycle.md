# 開発サイクル

- 文書番号: GV-DEV-001
- 版: 1.0
- 作成日: 2026-08-13

初期開発は**ドキュメント中心の TDD** で回す。ドキュメントが正典であり、コードもテストもドキュメントから導かれる。実測でドキュメントの想定が外れたときは、コードではなくまずドキュメントを直す。

---

## 1. サイクル

```
        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
  ①  設計書を書く / 更新する                        │
      docs/01〜03。何を作るか・なぜそうするかを確定   │
        │                                          │
        ▼                                          │
  ②  計画書のタスクへ落とす                          │
      docs/superpowers/plans/。テストコードまで書く   │
        │                                          │
        ▼                                          │
  ③  失敗するテストを書く                            │
      設計書の記述がそのまま assert になる            │
        │                                          │
        ▼                                          │
  ④  失敗を確認する                                 │
      「まだ実装が無い」以外の理由で落ちていないか     │
        │                                          │
        ▼                                          │
  ⑤  テストが通る最小限を実装する                     │
        │                                          │
        ▼                                          │
  ⑥  テストが通ることを確認する                       │
        │                                          │
        ▼                                          │
  ⑦  実測値を取る                                    │
      速度・精度・メモリ。推定値のままにしない         │
        │                                          │
        ▼                                          │
  ⑧  実測が設計書の想定と違えば設計書を直す ──────────┘
      コードを想定に合わせるのではなく、
      想定を事実に合わせる
```

**⑦→⑧ が本プロジェクトの核である。** 設計時点で以下のような想定の誤りが実測により覆っている。

| 設計時の想定 | 実測 | 反映先 |
|---|---|---|
| `contextualStrings` で用語辞書が効く | 出力が 1 文字も変わらない（無効） | 要件定義書 §2.6、詳細設計書 §4.4 |
| LLM 整形に毎回 2.23 秒かかる | 初回のみ。ウォーム後は中央値 0.389 秒（低負荷）／ 0.461 秒（負荷下、500ms 超 1/10）。**ただし `prewarm()` を呼ぶだけでは温まらず、捨て推論が要る** | 要件定義書 §2.7、基本設計書 §6、詳細設計書 §10 |
| `SpeechTranscriber` が最有力 | 日本語では `DictationTranscriber` が優位 | 要件定義書 §2.5、詳細設計書 §4.2 |

同じことが今後も起きる前提で進める。

## 2. ドキュメントの役割

| 文書 | 役割 | 変えてよいタイミング |
|---|---|---|
| [00-development-cycle.md](./00-development-cycle.md) | 本書。進め方の正典 | 進め方そのものを変えるとき |
| [01-requirements.md](./01-requirements.md) | 何を作るか、何を作らないか | スコープや目標値が変わるとき |
| [02-architecture.md](./02-architecture.md) | どう組み立てるか | 構造の判断が変わるとき |
| [03-detailed-design.md](./03-detailed-design.md) | どう実装するか、何を検証するか | API の実像が判明したとき |
| `docs/superpowers/plans/*.md` | 実行可能なタスク列 | 実装中に手順の誤りが判明したとき |

**コードだけを直してドキュメントを放置してはならない。** 設計書と実装が食い違った状態は、次に読む人（未来の自分を含む）を確実に誤らせる。

## 3. 数値の扱い

ドキュメントに書く数値には、必ず出所を添える。

| 種別 | 表記 | 例 |
|---|---|---|
| 実測値 | そのまま記載し、計測環境を明記 | 「103 秒の音声を 1.12 秒で処理（M3 / macOS 26.5.2）」 |
| 推定値 | **「推定値」と明記し、検証項目 V-x を割り当てる** | 「300 ms 以内（推定値。要計測 V-2）」 |
| 外部の報告 | 出典を明記 | 「外部ベンチでは Whisper Small 比 3 倍速と報告」 |

推定値を実測値へ置き換えたら、検証項目一覧（詳細設計書 §13）の該当行も更新する。

---

## 4. コミット

- 1 タスク = 複数の小さなコミット。テストと実装は分けず、「失敗するテスト → 実装 → 通過」を確認してから 1 コミットにまとめる
- 接頭辞: `feat:` / `fix:` / `test:` / `docs:` / `refactor:` / `chore:`
- 実測でドキュメントを更新したコミットは `docs:` で独立させ、何がどう変わったかを本文に書く

---

## 5. テストの方針

| 種別 | 対象 | 判定 |
|---|---|---|
| 純粋ロジック | プロンプト構築、ストア、キー判定、挿入経路の分岐 | 完全一致 |
| 認識精度 | 固定音声に対する書き起こし | **文字誤り率の閾値**。完全一致では OS 更新で壊れる |
| 性能 | 各段のレイテンシ | 目標値以内 |
| 実機依存 | マイク、Apple Intelligence、アクセシビリティ | 権限や機能が無い環境では**スキップ**する |

実機依存のテストは `.enabled(if:)` で条件付き実行にし、環境が揃わない場所でも `swift test` が緑になるようにする。

---

## 6. 検証項目（V-x）の運用

詳細設計書 §13 に一覧がある。各項目には「いつ実施するか」が紐付いている。

1. 実装が該当タスクへ到達したら検証を実施する
2. 結果を設計書へ記入する
3. 想定と違えば、設計書の該当箇所と、必要なら計画書のタスクも直す
4. 直した内容を `docs:` コミットで残す

**検証を飛ばして次のタスクへ進んではならない。** 推定値の上に実装を積むと、後で崩れたときに原因の切り分けができなくなる。
